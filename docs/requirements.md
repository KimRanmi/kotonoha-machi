# ことばのまち 요구사항 정의

> 일본어를 공부하기 위해 게임을 하는 것이 아니라, 일본어를 배우면서 내가 살고 싶은 작은 일본 마을을 만들어가는 게임이다.
> 그 마을에서 내 캐릭터로 직접 생활하고, 주민들과 실제 일본어로 이야기한다.

이 문서는 요구사항 정의 대화에서 사용자가 직접 확인(CONFIRMED)한 결정만 모은 것이다.
"구현 상태"는 `master` 브랜치(git 기록과 코드)를 확인해서 적었다. 마지막 동기화는 2026-10-12, `origin/master` 79b62f4 기준이다.
직접 실행해서 확인하지 못한 항목은 그렇게 표시했다. 요구사항을 정하지 않고 구현된 기능은 6장에 따로 모았다.

---

## 1. 핵심 루프

```
일본어 학습(테마) → 건물·아이템 해금 → 마을에 반영 → 주민과 일본어로 대화
      ↑                                                    │
      └── 대화 중 모르는 단어를 학습 목록에 추가 ←──────────┘
```

- 학습하는 날: 테마를 마치면 마을에 건물이 생긴다.
- 학습하지 않는 날: 새 콘텐츠는 없지만, 주민과 대화하며 관계가 깊어진다.
- 관계가 깊어지면 주민의 말투와 화제가 자연스럽게 달라진다.

## 2. 피하는 방향 (프로젝트 원칙)

- 단순 플래시카드 / 객관식 퀴즈 앱
- XP·레벨·출석만 강조하는 게임, 마을이 단순 배경인 구조
- 정해진 대사를 읽는 NPC, 선택지 몇 개만 고르는 대화
- 단순 AI 챗봇, "AI와 대화할 수 있다" 자체만 가치로 삼는 것
- SNS·커뮤니티·랭킹, 처음부터 지나치게 큰 3D 게임, 불필요하게 많은 시스템

## REQ-001 핵심 게임 루프

**목적:** 일본어 학습이 마을·관계의 성장으로 이어져, 사용자가 매일 돌아올 이유를 만든다.

**확정 사항**
- 학습→마을 성장 연결 단위는 "테마/레슨"이다.
- 학습하는 날: 테마 완료 → 새 한자·단어 습득 → 건물·꾸미기 아이템 해금. 꾸미기 아이템은 학습으로 얻는다.
- 학습하지 않는 날에도 주민 방문·대화로 관계(친밀도)가 쌓인다.
- 친밀도는 방문/대화 빈도로 오르고, 친밀도 보상은 새 대화 주제/에피소드다 (꾸미기 재화가 아님).
- 에피소드 속에서 새 어휘를 접하고, 학습 목록에 담아 다시 학습으로 연결한다.

**미정:** 테마의 구체적 크기, 학습을 오래 안 했을 때 마을에 부정적 신호(퇴색 등)를 줄지.

## REQ-002 플레이어 캐릭터

**목적:** 사용자가 마을을 관리하는 사람이 아니라, 자기 캐릭터로 직접 생활하는 사람이라는 느낌을 준다.

**확정 사항**
- 초기 커스터마이징은 처음부터 자유롭게 선택한다. 학습으로 해금되는 건 "추가" 아이템이다.
- 아이템은 순수 코스메틱이다 (능력치·게임적 효과 없음).
- 테마별 대표 아이템은 학습 내용과 의미가 연결된다 (예: 여행 테마 → 여행 가방). 나머지는 느슨한 보상이며, 모든 아이템을 한자에 1:1로 대응시키지는 않는다.
- 캐릭터는 마을 오픈맵을 직접 걸어 다니는 조작형 아바타다.

**미정:** 세부 항목과 UI는 REQ-009에서 정한다.

## REQ-003 마을 성장

**목적:** 학습 성과가 "들어가서 생활할 수 있는 공간"으로 마을에 반영되게 한다.

**확정 사항**
- 해금 단위는 개별 건물/시설이다.
- 완공된 모든 공간은 기능을 가진다 (학습 콘텐츠 열람형, 주민 대화 트리거형, 미니 상호작용형).
- 건물마다 담당 주민이 1:1로 연결된다.
- 마을은 로딩 전환 없이 걸어 다니는 하나의 오픈맵이다.
- 건설 방식과 위치는 REQ-013이 구체화한다 (즉시 완공, 사용자가 위치 선택).

**미정:** 공사 중 건물의 상호작용 여부, 맵의 실제 규모와 지역 경계, 건물당 주민이 1명으로 고정인지.

## REQ-004 일본어 학습

**목적:** 학습이 단순 암기가 아니라 실제 문맥에서 쓸 수 있는 일본어를 익히는 과정이 되게 한다.

**확정 사항**
- 학습 수준은 JLPT **N3~N1**이다 (처음에 N2~N1로 적었다가 N3~N1로 정정).
- 한 테마는 한자 → 단어 → 표현 → 예문으로 이어지는 혼합 세트다.
- 진행은 단계별 일괄이다: 한자 라운드 → 단어 라운드 → 표현 라운드 → 예문 라운드. 한 라운드를 끝내야 다음으로 간다.
- 각 라운드는 인식(뜻·읽는 법 확인) 위주로 가볍게 진행한다.
- 모든 라운드 뒤에 종합 복습이 있다: 질문에 배운 표현으로 직접 답해보는 간단한 문장/대답 연습 (생산·문맥 활동).
- 정답을 맞혀야 진행하는 정확도 게이트다. 일정 횟수 틀리면 힌트/정답을 보여줘서 막히지 않게 한다 (프로토타입은 3회).
- 진행 순서는 기본 커리큘럼 + 이후 일부 자유 선택이다.

**미정:** 재시도 횟수의 확정값, 힌트의 구체적 형태, 진행 표시 UI, 콘텐츠 출처, 테마 분량, 커리큘럼→자유 선택으로 바뀌는 시점.

**후속 안건: 테마 완료의 서버 검증 (2026-10-14, 방식 미정, 사용자와 논의 중)**
- 현재: 테마 6개(여행, 음식, 쇼핑, 직장, 날씨, 감정)의 내용과 해금 규칙은 프론트에만 있고, 서버는 `themeTitle` 문자열만 받아 기록한다. 존재하지 않는 테마나 선행 테마를 끝내지 않은 테마도 완료 처리되어 건물이 생길 수 있다.
- 방식 후보: A. Java에 테마 제목 목록 하드코딩 / B. 메타데이터(id, 제목, 수준, 선행 테마)만 공유 JSON 한 파일로 두고 서버가 존재 여부(400)와 선행 충족 여부(409)를 확인, 복습은 그대로 허용 / C. 문제·정답·판정까지 서버로 이전.
- 요구사항 쪽 기준: 이 게임은 1인용이고 순위·경쟁이 없다(피하는 방향). 퀴즈를 풀지 않고 완료만 호출하면 손해를 보는 사람은 본인뿐이므로, **퀴즈를 풀었는지까지 서버가 검증해야 한다는 요구사항은 없다.** 따라서 C는 요구사항상 필요하지 않다. 서버가 없는 테마·잠긴 테마의 완료를 거부하는 B 수준을 권장한다.
- 완료 기록의 키는 제목이다(기존 "여행" 기록 호환). 제목은 바꾸지 않는다.
- 사용자 확정 전이므로 방식은 미정이다.

**새 테마 추가 절차 (초안, 방식 확정 후 갱신)**
1. 콘텐츠 작성: 한자 3 / 단어 3 / 표현 2 / 예문 2 / 종합 복습 2문항. 일본어 정확성은 사용자가 검수한다.
2. 메타데이터 등록: id, 제목, 수준(N3~N1), 선행 테마.
3. 주민 연결: `THEME_RESIDENTS`에 기존 학습관 주민(새 주민 추가 없음) 연결. 연결이 없으면 건물에 주민이 없다.
4. 건물 배치 공간: 마을 맵에 빈 자리가 있는지 확인한다.

## REQ-006 주민

**목적:** 마을이 사람이 사는 곳이라는 느낌을 주고, 반복 방문의 동기가 되는 "관계"를 만든다.

**확정 사항**
- 주민은 건물 담당 주민과 떠돌이 주민이 섞여 있다.
- 친밀도는 단계형이고 5단계 이상으로 세분화한다. 최고 단계에서 멈추고, 그 안에서 새 에피소드가 계속 추가된다.
- 성격 차별화는 우선 대화 주제/관심사로 한다 (말투·행동 차별화는 보류).
- 친밀도 표시는 **서술형 문구만** 쓴다. 수치·퍼센트 게이지·"레벨업" 토스트는 쓰지 않는다. 현실의 관계처럼 정확히 얼마나 남았는지 알 수 없게 한다.
- 관계가 깊어졌다는 신호는 주민의 말투와 화제가 자연스럽게 달라지는 것으로만 전달한다.
- 친밀도는 별도의 주민 목록 화면에서 서술형 텍스트로 확인한다.

**프로토타입 값:** 6단계, 누적 대화 0/3/8/15/25/40회에서 단계 상승. 문구는 "아직 낯선 사이예요" ~ "둘도 없는 친구가 됐어요".

**미정:** 단계 명칭과 상승 횟수의 최종값, 떠돌이 주민의 등장 조건, 주민 수 상한.

## REQ-007 주민과의 자유 대화

**목적:** 정해진 대사나 선택지가 아니라, 실제로 일본어를 쓰는 상호작용 자체를 핵심 재미로 만든다.

**확정 사항**
- 사용자가 일본어로 말하거나 타이핑하면 주민이 이해하고 맥락에 맞는 일본어로 답한다.
- 텍스트 자유 대화도 음성과 같은 정식 모드다.
- 텍스트 입력은 **앱 자체에 로마자→가나 자동 변환**을 내장한다 (OS의 일본어 입력기 설정과 무관). 한자 변환은 범위 밖이고, 히라가나만으로 쓴 문장도 정상 입력이다.
- 주민은 이전 대화를 전부 기억하지 않고, 인상적인 발언만 선별적으로 기억한다.
- 대화 중 단어를 탭하면 "학습 목록에 추가" 버튼만 뜨는 최소 개입 팝업이다. 뜻·읽는 법·예문은 그 자리에서 보여주지 않고 복습 목록에서 확인한다.
- 주민 답변의 한국어 번역은 **기본으로 숨기고, 사용자가 눌렀을 때만 보여준다.** 번역이 항상 붙어 있으면 일본어를 읽지 않고 번역만 읽게 되어 "일본어로 직접 대화한다"는 핵심 경험과 부딪히기 때문이다. (구현 완료: PR #10, 메시지별 "번역 보기/숨기기" 버튼.)

**미정:** 기억 선별 기준과 유지 기간, 텍스트·음성 모드의 대화 기록 공유 여부.

## REQ-008 음성 대화

**목적:** 텍스트를 넘어 말하기·듣기로 확장해, 실제 사람과 이야기하는 몰입감을 준다.

**확정 사항**
- 음성 입력은 토글형이다: 한 번 누르면 녹음 시작, 다시 누르면 종료.
- 주민이 잘 이해하지 못하면 오류 메시지 대신 실제 대화처럼 자연스럽게 되묻는다.
- 주민의 음성 답변에는 항상 텍스트 자막이 함께 표시되고, 자막에도 단어 탭 상호작용이 적용된다.
- 프로토타입은 브라우저 내장 Web Speech API를 쓴다 (별도 유료 API 없음).

**미정:** 발음 교정, 일본어 수준 판단·난이도 조절, 완전히 인식 못 했을 때의 세부 처리, 텍스트↔음성 전환 방식.

## REQ-009 캐릭터 커스터마이징

**목적:** REQ-002의 꾸미기 범위와 화면 흐름을 구체화한다.

**확정 사항**
- 핵심 소수 항목(헤어스타일, 상의, 액세서리 정도)으로 시작하고 이후 확장한다.
- 성별 구분 없이 모든 항목을 자유롭게 조합한다.
- 계절 의상은 실제 현실 계절과 연동한다.
- 꾸미기는 언제든 열 수 있는 전용 메뉴/버튼으로 진입하고, 탭으로 카테고리를 전환하며, 선택 즉시 캐릭터에 반영(실시간 미리보기)된다.

**미정:** 항목 목록과 확장 순서, 자동 저장 vs 저장 버튼, 아직 해금 안 된 아이템을 잠긴 채 보여줄지, 모달 vs 전체 화면.

## REQ-010 학습과 대화의 연결

**목적:** "학습 → 실제 사용 → 반복 노출 → 기억 강화" 순환 고리를 규칙으로 만든다.

**확정 사항**
- 테마를 학습하면 그 어휘가 연결된 건물/주민의 대화에 확정적으로 포함된다.
- 대화 중 "학습 목록에 추가"한 단어는 일정 개수가 모이면 자동으로 "복습 테마"로 묶이고, 완료하면 일반 테마와 동일한 보상(건물·아이템)을 받는다.
- 이미 배운 단어의 반복 노출은 문맥에 맞을 때만 자연스럽게 한다 (강제 반복 없음).

**미정:** 복습 테마가 생기는 단어 개수, 어휘 노출을 확정적으로 보장하는 구현 방식.

## REQ-011 장기적인 성장/콘텐츠

**확정 사항**
- 마을 확장에는 상한이 있다. 다 채운 뒤에는 주민과의 관계 심화와 디테일 중심으로 전환한다.
- 계절/시즌에 따른 반복 이벤트(축제 등)가 주기적으로 있다.

**미정(의도적 보류):** 학습 콘텐츠를 다 마친 뒤의 구조, 마을 상한의 구체적 규모, 이벤트의 형태와 빈도.

## REQ-012 캐릭터 외형에 대한 주민의 인식

**확정 사항**
- 구현한다. 평범한 의상에는 반응하지 않고, 축제·계절 의상 같은 특별 아이템에만 주민이 반응한다.
- 반응은 대화 시작 인사에 한 번이 아니라 대화 맥락 전반에 지속적으로 반영된다.

**미정:** 특별 아이템의 판별 기준, 여러 개 동시 착용 시 우선순위, 대화 생성에 정보를 넘기는 방식.

## REQ-013 학습 완료 → 마을 반영

**확정 사항**
- 테마를 완료하면 즉시 마을 화면으로 자동 전환되고 짧은 건설 연출이 나온다.
- 건설은 실제 대기 시간 없이 즉시 완공된다 (연출만, 타이머 없음).
- 건물의 위치는 사용자가 마을 맵의 빈 자리를 직접 골라 배치한다.
- **건물은 테마를 처음 완료할 때만 생긴다.** 같은 테마를 다시 하는 것은 복습으로 치고 건물은 새로 생기지 않는다. 건물 수가 실제 학습량을 보여주게 하기 위해서다. (구현 완료: PR #10, 완료한 테마 기록을 저장하고 재완료 시 "복습 완료!"로 표시.)

**미정:** 배치 가능한 자리가 정해진 슬롯인지 완전 자유인지, 재배치 가능 여부, 복습으로 다시 한 테마를 마쳤을 때 주는 보상이 있는지.

## REQ-014 내 집

**목적:** 학습과 무관하게 처음부터 나만의 거점을 갖고, 그 안을 직접 꾸민다.

**확정 사항**
- "내 집"은 게임 시작부터 존재한다 (학습으로 해금되지 않음).
- 마을 맵 위의 위치는 고정이 아니라, 게임을 처음 시작할 때(온보딩) 사용자가 직접 배치한다 (REQ-013과 같은 방식).
- 집에 들어가면 내부 공간이 있다. 내부는 다른 건물과 같은 **캐릭터가 걸어 다니는 방**이고(REQ-016), 내 집에만 가구를 옮길 수 있는 **꾸미기 모드**가 추가된다.
- 가구는 처음부터 기본 몇 개가 제공된다.
- 가구는 자유 위치에 놓을 수 있고, 가구끼리 겹치지 않도록 충돌 체크가 있다.
- "내 집"은 다른 건물과 겉모습이 구분된다: 전용 색과 아이콘, 그리고 "내 집" 표시.
- 처음 시작할 때의 순서는 **캐릭터 만들기 → 집 배치**다. 캐릭터 꾸미기(REQ-009)는 아직 없으므로, 첫 구현에서는 집 배치만 하되 캐릭터 만들기 단계가 앞에 들어갈 자리를 남겨둔다.
- 첫 구현(v1)의 가구는 처음 제공되는 기본분만이다.

**미정 — 추가 가구 획득 방식:** 사용자 아이디어는 "이벤트 형식"이다 (예: 접속하면 포인트를 주고 그걸로 가구를 얻는 식). 검토할 점은 세 가지다.
- 프로젝트 원칙에서 출석·연속 학습만 강조하는 구조는 피하기로 했다. 보조 보상으로는 가능하지만 핵심이 되면 안 된다.
- 접속 날짜를 믿으려면 서버가 시각을 판단해야 해서 서버 이전(REQ-015)과 함께 해야 한다.
- 포인트와 교환 화면까지 만들면 범위가 커진다. 시즌 이벤트(REQ-011) 보상으로 가구를 주는 방식이 더 가볍다.
- 그 외 후보: 테마 완료 시 그 테마와 어울리는 가구 해금, 주민과 친해지면 선물.

이 항목은 결정 전까지 v1에서 제외한다.

## REQ-015 기술 스택·서버 아키텍처

원래 브리핑은 기술 스택을 미결정으로 두었고, 구현 단계에서 아래처럼 확정했다. 포트폴리오용 프로젝트라는 목적을 반영한다.

**확정 사항**
- 프론트엔드: Next.js 16 (App Router). `/api/*`는 `next.config.ts`의 rewrites로 백엔드에 프록시한다.
- 백엔드: Spring Boot 4.1.1, Gradle, Java 25 (`backend/`, 패키지 `com.kotonoha`). 주민 대화는 Gemini API를 호출한다.
- 저장소: PostgreSQL + Flyway. 인증은 이메일/비밀번호 가입(닉네임 포함)이고, 15분짜리 JWT 접근 토큰은 메모리에 두며 회전하는 httpOnly refresh 쿠키로 갱신한다 (커밋 bf8ec2a).
- Docker 전체 실행(compose `full` 프로파일)을 지원한다.
- `localStorage`의 학습 단어, 건물, 테마 완료 기록, 내 집, 온보딩 데이터는 서버 API로 이전했다 (커밋 cb5f592, 테이블 `learned_words`, `completed_themes`, `pending_buildings`, `placed_buildings`, `homes`, `onboarding_steps`). 이때 브라우저에 이미 쌓인 기존 테스트 데이터는 서버로 이전하지 않고 버렸다 (마이그레이션 코드 없음).
- `localStorage`는 동기, 서버 API는 비동기라서 저장 함수를 부르는 화면 쪽도 대기 방식으로 고쳐야 할 수 있다.
- 저장 코드는 `lib/storage.ts`에 모아 두고, 화면 코드가 `localStorage`나 `fetch`를 직접 호출하지 않는다.

**남은 계획:** rate limit, 마지막 위치 저장(REQ-019).

## REQ-016 건물 내부 공간

**목적:** 건물이 겉모습뿐인 배경이 아니라, 실제로 들어가서 주민을 만나는 공간이 되게 한다. REQ-003의 "마을은 단순한 배경이 아니다"를 구체화한다.

**확정 사항**
- **모든 건물**에 들어갈 수 있는 내부 공간이 있다: 주민이 운영하는 건물(카페·상점·마을회관), 테마로 짓는 학습관, 내 집.
- 건물에 다가가 Enter/Space로 들어가고, 내부는 캐릭터가 직접 걸어 다니는 방이다. 모든 내부를 같은 방식(걷는 방)으로 통일한다.
- 주민 건물의 내부는 가구가 **미리 배치**되어 있고 사용자가 바꿀 수 없다.
- 주민은 건물 안에 서 있고, 가까이 가서 Enter로 대화를 시작한다 (대화는 지금의 작은 모달을 그대로 쓴다). 건물 밖에서 바로 대화가 뜨는 방식은 없어진다.
- 내 집에만 가구를 옮길 수 있는 꾸미기 모드가 있다 (REQ-014).

**구현 방침(제안, 사용자 확정은 아님):** 건물 종류별 방 템플릿(카페, 상점, 마을회관, 학습관)을 두고, 테마로 지은 학습관은 공통 학습관 템플릿을 쓴다. 테마마다 방을 새로 디자인하지 않아 콘텐츠 부담을 줄인다.

**미정:** 테마마다 다른 방을 둘지, 방에서 나가는 방식의 세부 UI, 건물 안 주민이 시간대에 따라 움직이는지.

**상태:** 확정

## REQ-018 비주얼 디자인 방향

**목적:** 지금까지 기능 검증 위주로 만들어 사용자가 만족하지 못하는 화면 전체를, 일관된 "아기자기한 일본 마을" 분위기로 바꾼다.

**확정 사항**
- 기준 분위기: **동물의 숲**(따뜻한 크림 바탕, 둥글고 도톰한 UI), **산리오 느낌**(점 눈과 볼 터치만 있는 단순한 얼굴, 파스텔), **일본 카페 감성**(크림·말차·나무·벚꽃 톤, 둥근 일본어 폰트, 노렌·등롱 같은 소품). 일본스러운 느낌을 살린다.
- 시안(대화창): 크림 배경, 도톰한 둥근 테두리, 점선 구분선, 둥근 일본어 폰트(Zen Maru Gothic), 말차색 사용자 말풍선, 벚꽃·말차·나무색 팔레트. 사용자가 "귀엽다"며 확정했다.
- 작업 순서: **화면 전체 스타일 먼저 → 캐릭터**.
- 캐릭터는 코드(SVG)로 부품을 조합해서 만든다. 가게 주민은 **가게 분위기에 맞는 부품과 색으로 자동 생성**한다 (예: 카페 주인은 앞치마와 갈색 톤). 이 부품 시스템이 캐릭터 꾸미기(REQ-009)의 바탕이 된다.
- 산리오 등 기존 캐릭터를 그대로 따라 그리지 않는다. 분위기만 닮은 새 캐릭터를 만든다 (저작권).

**방향 변경 (사용자 확정, 2026-10-12):** 구현 과정에서 화면이 3D 방향으로 바뀌었고, 사용자가 이 방향이 맞다고 확정했다. 위 "확정 사항" 중 아래 항목은 이 변경이 우선한다.
- 마을 지도: 아이소메트릭(비스듬히 내려다보는 3D) 시점의 로우폴리 스타일. 카메라가 캐릭터를 따라가고, 울타리 밖으로 숲·호수가 이어지며, 구름 그림자·새·나비 같은 살아 있는 디테일이 있다.
- 건물 내부: three.js로 만든 3D 방 (지연 로딩, 조명과 그림자, 사실적인 가구).
- 캐릭터: 3D 형태(주민마다 외형이 다른 character3d)와 걷기 애니메이션. "코드(SVG)로 부품을 조합한다"던 초기 결정은 3D 형태로 바뀌었다.
- 라이브러리: three.js 사용을 허용한다. 1단계 프롬프트의 "새 라이브러리 금지"는 더 이상 적용하지 않는다.
- 위 "공통 시안(대화창)"과 "마을 맵 시안"은 처음 방향을 기록한 것으로, 마을 지도와 건물 내부에는 더 이상 적용되지 않는다.

**미정:** UI(대화창, 버튼)의 모서리 모양(현재 직각, 처음 시안은 둥근 모서리), 처음 팔레트와 폰트(크림, 말차, 벚꽃, Zen Maru Gothic)를 어디까지 유지할지, 캐릭터 꾸미기(REQ-009)를 3D 캐릭터에서 어떻게 할지, 다크 모드 지원.

**상태:** 확정 (3D 방향 반영)

## REQ-019 마지막 위치 이어하기

**목적:** 다시 접속했을 때 마지막에 있던 곳에서 이어서 시작한다.

**확정 사항**
- 마지막 위치(마을인지 어느 건물 안인지, 그리고 좌표)를 저장하고, 다시 접속하면 그 위치에서 시작한다.
- **건물 안에 있었다면 그 건물 안에서 시작한다** (마을 입구로 보내지 않는다).
- 사용자마다 자기만의 마을을 가진다. 여러 사용자가 같은 마을에서 만나는 멀티플레이는 하지 않는다 (사용자 의견: 다른 사용자와 섞이면 한국어가 끼어들어 일본어 몰입이 깨진다. 처음 브리핑의 SNS·커뮤니티 제외와도 일치). — 이 부분은 사용자 발언을 해석한 것이라 확인이 필요하다.
- 저장은 PostgreSQL에 한다 (한 사용자당 한 줄의 작은 데이터라 NoSQL이 필요 없다).

**구현 방침(제안, 사용자 확정은 아님):** 캐릭터가 걸을 때마다(매 프레임) 서버에 보내지 않는다. 건물 입장/퇴장 때, 걷는 중에는 몇 초 간격이나 멈췄을 때, 브라우저를 닫을 때 저장한다.

**미정:** 저장된 건물이 사라졌거나 들어갈 수 없을 때의 대체 위치(예: 마을 입구), 로그아웃 후 재로그인에도 동일하게 적용할지.

**상태:** 확정

아래 REQ-017, REQ-020~024는 다른 작업 세션이 먼저 구현했고, 2026-10-12에 사용자가 "요구사항으로 정리하라"고 해서 **구현된 동작을 요구사항으로 채택**한 것이다. 내용은 커밋 기록과 코드로 확인한 동작이며, 직접 실행해서 확인하지는 못했다.

## REQ-017 로그인이 첫 관문

**목적:** 학습 데이터, 건물, 대화 기록이 계정 기준으로 서버에 저장되므로, 로그인 없이는 쓸 수 없게 한다.

**확정 사항**
- 로그인이 첫 관문이다. 로그인하지 않으면 어느 화면도 쓸 수 없고 로그인 화면으로 이동한다 (커밋 설명 기준으로 게스트 모드는 없다).
- 접근 토큰(15분, 메모리)과 회전하는 httpOnly refresh 쿠키로 로그인 상태를 유지한다 (REQ-015).

**미정:** 비밀번호 재설정, 소셜 로그인 같은 계정 기능은 확인하지 못했다.

**상태:** 확정

## REQ-020 닉네임

**목적:** 주민이 사용자를 이름으로 불러서, 주민과의 관계가 더 개인적으로 느껴지게 한다.

**확정 사항**
- 가입할 때 닉네임을 정한다. 규칙은 2~12자의 글자, 숫자, 밑줄(_)이다. 가입 중에 중복 확인을 한다. 가입 후에도 닉네임을 바꾸는 화면이 있다.
- 주민은 사용자를 닉네임으로 부른다. 일본어 대화에서는 닉네임을 **가타카나로 바꾼 표기**로 부른다.

**미정:** 닉네임 변경 횟수 제한, 부적절한 닉네임 거르기.

**상태:** 확정

## REQ-021 건물 안 사람들

**목적:** 건물 안이 주인 한 명만 서 있는 빈 방이 아니라, 사람들이 실제로 지내는 공간처럼 느껴지게 한다 (REQ-006, REQ-016 확장).

**확정 사항**
- 각 건물 안에는 주인 외에 직원, 공동 주인, 손님, 학생이 여러 명 있다. 모두 이름과 성격이 있는 "주민 친구"이고 대화할 수 있다 (새 주민 13명).
  - 카페: 미유(주인), 켄타(제빵사), 사쿠라(대학생 손님), 다이스케(직장인 손님), 나나(방과후 알바생)
  - 상점: 타쿠미(주인), 모모카(점원), 소타(물건 정리 점원), 요시코(장보러 온 할머니)
  - 마을회관: 하나(직원), 히로시, 미나(직원), 이와오(어르신)
  - 학습관: 린(여행 이야기), 유이, 료, 아오이(학생)
- 사람들은 가만히 서 있지 않고 서 있기, 앉기, 돌아다니기를 반복한다. 서로 충돌하지 않고, 이름이 머리 위에 표시된다.
- 플레이어는 가장 가까운 사람과 대화를 시작한다.

**미정:** 친밀도(REQ-006)를 사람별로 따로 쌓는지, 시간대에 따라 사람이 바뀌는지.

**상태:** 확정

## REQ-022 카페 주문·서빙·좌석

**목적:** 식당에서 주문하고 먹는 일상 장면을 게임 안에서 겪게 해서, 일상 일본어를 쓸 상황을 만든다.

**확정 사항**
- 카페에서 음료와 케이크를 주문한다. 메뉴: コーヒー(커피) 400円, 紅茶(홍차) 400円, いちごのショートケーキ(딸기 쇼트케이크) 550円, チーズケーキ(치즈케이크) 500円.
- 주문하면 직원이 음료는 기계에서, 케이크는 진열대에서 준비해 쟁반을 들고 길을 찾아 플레이어에게 가져온다. 건네받고 먹는다.
- 좌석에 앉을 수 있다. 앉으면 음식이 테이블 위에 놓이고 앉은 채로 먹는다. F 키나 이동 키로 일어난다.
- 주문 방법은 메뉴에서 고르는 것과 일본어로 직접 말하는 것(REQ-023) 두 가지다.

- 가격(円)은 **표시만 한다.** 돈이나 포인트를 쓰는 지불 시스템은 없다 (사용자 확인). 가격은 일본어로 금액을 말하고 듣는 학습 상황을 만들기 위한 것이다.

**미정:** 없음.

**상태:** 확정

## REQ-023 일본어로 주문하고 사기

**목적:** 단어를 외우는 게 아니라, 실제 상황에서 일본어로 말해서 원하는 걸 얻는 경험을 준다 (REQ-007, REQ-010 확장).

**확정 사항**
- 카페(주문)와 상점(구매)에서 직원에게 일본어로 말해서 주문한다. 상점은 선반이나 냉장고에서 물건을 가져다준다.
  - 상점 상품: りんご(사과) 150円, パン(빵) 200円, 牛乳(우유) 180円, お茶(차) 130円.
- 주문은 말 속에 품목 단어와 부탁하는 말(「ください」「お願い」「ほしい」 등)이 있으면 인식한다. 가타카나/히라가나, 전각/반각 차이는 무시하고, 일부 틀리거나 줄여 말해도 알아듣는다. 「いらない」 같은 거절 표현이면 무시한다.
- 직원의 답변은 AI가 하고(말투, 되묻기, 없는 물건 사과), 직원의 답에 접수 표현(「かしこまりました」「少々お待ちください」 등)이 있으면 접수된 것으로 본다.
- 주문 화면은 주문할 때 쓰는 일본어 문장과 한국어 뜻을 함께 보여준다 (예: 「コーヒーをひとつください。」).
- **주문에 쓴 단어는 학습 단어 목록에 자동으로 저장된다** (REQ-010의 "대화에서 모은 단어"를 다른 방식으로 구현).
- 직원은 자기 가게의 메뉴와 가격을 알고 있고, 틀린 일본어도 알아듣되 올바른 표현을 자연스럽게 되풀이해 준다.

**미정:** 메뉴와 상품의 확장, 가게별 매진 같은 상태.

**상태:** 확정

## REQ-024 듣기 모드

**목적:** 글자를 읽지 않고 귀로 이해하는 연습을 하게 한다 (REQ-008 확장).

**확정 사항**
- 듣기 모드를 켜면 주민의 말을 음성(TTS)으로 읽어 주고 답변 텍스트는 가려서 보인다. 켜짐 상태는 브라우저에 저장된다.
- 현재는 건물 안 대화에서 켜고 끌 수 있다.

**미정:** 가려진 텍스트를 다시 보는 방법의 세부, 마을이나 일반 대화에도 적용할지.

**상태:** 확정

## REQ-025 AI(Gemini) 호출 실패 처리

**목적:** 외부 AI가 일시적으로 실패해도 대화 흐름과 기록이 깨지지 않고, 사용자가 무슨 일인지 알 수 있게 한다.

**발견 경위:** 2026-10-14 로컬 대화 중 Gemini 503(과부하)로 "응답 가져오기 실패"가 떴다. 코드 버그가 아니라 외부 일시 장애이며, 지금은 원인 구분 없이 일반 실패 메시지만 나온다.

**확정 사항**
1. 장애 유형 구분: ① 일시 장애/한도(503, 429, 타임아웃, 네트워크) ② 설정 문제(401, 403) ③ 응답 형식 오류(JSON 파싱 실패). 사용자 메시지는 ①은 "잠시 후 다시 시도", ②③은 "문제가 생겼어요"로 단순화하고, 상세 원인은 서버 로그에만 남긴다.
2. 자동 재시도: ①에 한해 짧은 백오프로 최대 2회, 총 대기 약 10초 이내. ②③은 재시도하지 않는다.
3. 폴백: 보조 모델 대체는 하지 않는다(우선 단순하게). 최종 실패 시 주민 대사로 대체하지 않고 일반 에러 안내만 보여준다(실패한 말이 대화 기록처럼 보이지 않게).
4. 화면: 재시도/입력 중 상태 표시, 실패 시 "다시 시도" 버튼, 입력한 메시지는 지우지 않고 유지.
5. 기록 정합성: 실패한 턴의 사용자 메시지는 저장하지 않는다. 친밀도는 성공한 대화에서만 오른다. 중복 전송은 막는다.
6. 부가 호출(번역 등) 실패는 본 응답 표시에 영향을 주지 않는다. 번역 자리에만 "번역 실패 · 다시 시도"를 보인다.
7. 로그: 장애 유형별로 구분해 남긴다. 알림 연동은 하지 않는다.

재시도 총 대기 상한은 약 10초로 확정. 음성 대화 중 실패도 같은 방식(에러 안내만, 다시 말하기)으로 처리한다.

**미정:** 없음.

**상태:** 확정

## 4. 문서 간 확인이 필요한 부분

작성하면서 서로 어긋나거나 정의가 비어 있는 곳을 발견해 적어둔다. 사용자 결정이 필요하다.

1. **꾸미기 아이템의 획득 방식**: REQ-001/002는 "꾸미기 아이템은 학습으로 얻는다"인데, REQ-014는 가구를 처음부터 제공한다. 시작 제공분과 추가 획득을 어떻게 나눌지 정해야 한다 (REQ-014 미정 1번과 같은 문제).
2. **건설 방식**: REQ-003의 "점진적 건설"과 REQ-013의 "즉시 완공(연출만)"이 다르다. REQ-013이 구체화한 최신 결정으로 본다.
3. ~~**한국어 번역**~~ → **결정됨, 구현됨**: 기본 숨김, 눌러야 표시 (REQ-007).
4. ~~**같은 테마의 반복 완료**~~ → **결정됨, 구현됨**: 건물은 처음 완료할 때만 생김 (REQ-013).
5. **테마 분량**: 현재 테마는 "여행" 1개뿐이라 순환 고리가 한 바퀴 돌면 이어갈 콘텐츠가 없다. 특히 테마가 1개뿐이라, 처음 완료하면 건물이 생기고 그 뒤로는 새로 얻을 게 없는 상태다.
6. **추가 가구 획득 방식**: REQ-014 참고. 이벤트 형식 아이디어가 나왔고 결정 전까지 v1에서 제외했다.

## 6. 요구사항을 정하지 않고 구현된 기능 (사용자 확인 필요)

다른 작업 세션에서 구현되어 master에 들어갔지만, 요구사항 정의 대화에서 정한 적이 없는 것들이다. 커밋 메시지로 확인한 내용이고, 직접 실행해서 확인하지는 못했다. 각각 **요구사항으로 확정할지, 되돌릴지, 지금처럼 둘지**를 정해야 한다.

### 6-1. 확정한 요구사항과 어긋나 보이는 것

| 항목 | 확정한 요구사항 | 커밋 기록상의 현재 |
|---|---|---|
| ~~화면 분위기 (REQ-018)~~ → **결정됨: 3D 방향 확정** | 둥글고 도톰한 모서리의 파스텔 크림 톤 (사용자가 "귀엽다"며 확정) | "UI 모서리를 전부 직각으로(모든 radius 0)", "대화창 박스 테두리 제거, 색으로만 구분" 커밋이 있고, 마을 지도는 동물의 숲풍, 지브리풍 등으로 여러 번 바뀐 뒤 아이소메트릭 로우폴리 3D로 갔다. 마지막 모습은 직접 보고 확인해야 한다. |
| ~~새 라이브러리~~ → **결정됨: three.js 허용** | 1단계 프롬프트에 "새 라이브러리 추가 금지" | 건물 내부를 three.js로 만든 3D 방으로 바꿨다 (지연 로딩). |

| **친밀도 표시 (REQ-006)** | 수치 없이 서술형만 | 이 부분의 변경 기록은 없다 (유지된 것으로 보임). |

### 6-2. 새로 생긴 기능 → 2026-10-12에 요구사항으로 채택함 (REQ-017, REQ-020~024)

1. **닉네임**: 가입 시 닉네임과 중복 확인, 주민이 사용자를 닉네임으로 부른다. 닉네임을 가타카나로 바꿔서 부르는 처리도 있다 (REQ-007 확장).
2. **로그인이 첫 관문 (REQ-017, 사용자가 요청)**: 모든 화면을 로그인 뒤로 이동. 게스트 모드가 없는 것으로 보인다.
3. **방 안 주민 대폭 추가**: 건물 안에 직원, 공동 주인, 손님, 학생 등 주민이 여러 명 있고(새 주민 12명, 서버·클라이언트), 서고 앉고 돌아다니는 행동과 충돌 처리가 있다. 이름이 머리 위에 표시되고 가장 가까운 사람과 대화한다 (REQ-006 확장, 방 안의 "떠돌이"에 가까움).
4. **카페 주문**: 메뉴, 직원이 기계와 진열대에서 음식을 준비해 쟁반을 들고 길 찾기로 플레이어에게 가져온다. 좌석에 앉아서 먹을 수 있고, F 키나 이동으로 일어난다.
5. **일본어로 주문하기**: 직원과의 대화가 메뉴 단어와 요청을 이해해서 서빙을 시작한다. 직원 프롬프트가 메뉴를 안다.
6. **상점 구매**: 일본어로 말해서 사고, 가격이 있다. 주문 시스템을 일반화했다.
7. **듣기 모드**: 주민 말을 TTS로 읽어 주고 텍스트는 숨기는 모드 (REQ-008, REQ-010 확장).
8. **학습 루프**: 주문할 때 쓴 단어가 학습 단어 목록에 자동 저장된다 (REQ-010의 "대화에서 모은 단어" 일부를 다른 방식으로 구현).
