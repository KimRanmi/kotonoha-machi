# ことばのまち 요구사항 정의

> 일본어를 공부하고, 내가 살고 싶은 작은 일본 마을을 만들어가는 게임이다.
> 그 마을에서 내 캐릭터로 직접 생활하고, 주민들과 실제 일본어로 이야기한다.

요구사항은 처음부터 다시 정하는 중이다. 확정된 내용부터 이 문서에 쌓아간다. 이전에
만들었던 코드와 기획은 git 기록에 그대로 남아있어서, 필요하면 언제든 참고할 수 있다.

---

## MVP 범위

| 기능 | 포함 여부 | 비고 |
|---|---|---|
| 로그인 / 회원가입 | ✅ 포함 | 이메일+비밀번호, 이메일 인증, 소셜 로그인 |
| 프로필 (닉네임 수정 + 캐릭터 꾸미기) | ✅ 포함 | |
| 테마 학습 (오늘의 학습) | ✅ 포함 | 1순위 기능 |
| 주민과의 대화 (채팅) | ✅ 포함 | 2순위 기능, 타이핑+음성, 발음 체크 |
| 일본어 입력 도우미 | ✅ 포함 | 로마자 자동 변환 + 화면 가상 키보드 |
| 학습 단어장 | ✅ 포함 | |
| 주민 음성 (TTS) | ✅ 포함 | 브라우저 TTS, 주민마다 다른 목소리 (결제 없이) |
| 마을 화면 + 캐릭터 이동 | ✅ 포함 (구조상 필수) | 자유 이동, 구역 나눠 연결, 건물은 아이콘 클릭 입장, 배경 2D + 캐릭터만 3D |
| 마을/집 꾸미기 | ⏳ 나중 | 3순위 기능, MVP 이후로 미룸 — 테마 학습·주민 대화(1·2순위)부터 먼저 |
| 앱(모바일) 배포 | ⏳ 나중 | PWA 또는 Capacitor로 추후 고려 |

## 확정된 요구사항

### 핵심 루프

**확정 사항:**

```
일본어 학습(테마) → 꾸미기 아이템 해금 → 마을에 반영 → 주민과 일본어로 대화
      ↑                                                    │
      └── 대화 중 모르는 단어를 학습 목록에 추가 ←──────────┘
```

- 학습→마을 성장 연결 단위는 "테마/레슨"이다.
- 학습하는 날: 테마 완료 → 새 한자·단어 습득 → 꾸미기 아이템 해금. 꾸미기 아이템은
  학습으로 얻는다.
- 학습하지 않는 날에도 주민 방문·대화로 관계(친밀도)가 쌓인다.
- 친밀도는 방문/대화 빈도로 오르고, 친밀도 보상은 새 대화 주제/에피소드다(꾸미기 재화가
  아님).
- 대화 중 모르는 단어를 학습 목록에 추가하면, 다시 학습으로 연결된다.
- 관계가 깊어지면 주민의 말투와 화제가 자연스럽게 달라진다.

로그인 후 우선순위는 다음 순서다.

1. 오늘의 새 단어·문법 배우기
2. 주민과 대화하기 (회화 능력 향상 목적)
3. 마을/집 꾸미기

- 하루에 진행할 수 있는 테마는 **1개로 제한한다**(오늘의 테마만 진행, 서버도 강제). Gemini API 호출 비용은
  별도로 모니터링한다.
- 주민과의 대화량(하루 메시지 수)은 제품 제한이 없다. 요금 폭탄을 막는 악용 방지용 넉넉한 상한(사용자당 하루 200회, 한국 시간 기준)만 두고, 걸리면 오류가 아니라 "주민이 졸려요" 연출로 보여 준다.
- 서비스는 완전 무료로 간다. MVP는 게임 콘텐츠를 증명하는 데 집중하고, 수익화는 출시 이후
  별도로 검토한다.

**미정:** 테마의 구체적 크기, 학습을 오래 안 했을 때 마을에 부정적 신호(퇴색 등)를 줄지.

### 로그인 / 회원가입

**확정 사항:**
- 이메일 + 비밀번호로 가입한다.
- 가입 시 이메일로 숫자 인증 코드를 보내고, 그 코드로 확인해야 가입이 완료된다.
- 가입할 때 **닉네임**도 함께 받는다 — 마을 주민들이 나를 부를 때 쓰는 이름이다. 다른
  사람과 중복되지 않아야 하며, 가입 중에 중복 여부를 확인할 수 있어야 한다.
- 로그인하지 않으면 다른 화면에 접근할 수 없다(로그인 필수).
- 이메일/비밀번호 외에 소셜 로그인도 지원한다. 구글·카카오·네이버 세 곳을 지원한다
  (`SocialProvider`에 이미 구현됨).
- **로그아웃**: 세션을 즉시 무효화한다.
- **비밀번호 재설정(분실 비밀번호)**: 가입 때와 같은 이메일 인증 코드 방식으로 본인 확인
  후 새 비밀번호를 설정할 수 있다. MVP 범위에 포함한다.
- **이메일 인증 코드 보안**: 코드 유효시간은 10분, 코드 확인 실패는 5회까지 허용하고
  초과하면 거부한다(둘 다 이미 구현됨, `AuthService`). 재발송(resend) 요청에는 60초
  쿨다운을 둬서 짧은 시간 안에 연속 재발송하는 것을 막는다(현재는 쿨다운이 없어 추가
  필요).
- **회원 탈퇴**: 소프트 삭제로 처리한다(`UserStatus.WITHDRAWN`, 행은 보존하고 상태만
  변경). 탈퇴 즉시 로그인이 막히고 세션도 무효화된다. 비밀번호가 있는 계정은 현재 비밀번호
  재확인 후 탈퇴, 소셜 전용 계정은 재확인 없이 탈퇴한다. 자세한 이유와 한계는
  [`docs/decisions/0006-account-deletion.md`](docs/decisions/0006-account-deletion.md)
  참고.

### 프로필 (닉네임 수정 + 캐릭터 꾸미기)

**확정 사항:** 닉네임을 나중에 수정할 수 있고, 내 캐릭터 꾸미기도 같은 화면에서 할 수
있어야 한다. 가입 때와 마찬가지로 닉네임은 중복 확인이 필요하다. MVP 범위에 포함한다.
꾸미기 항목은 **피부색 / 머리색 / 헤어스타일 / 옷 / 옷 색 / 신발** 여섯 가지 축으로 고른다(와이어프레임의 다섯 축에 옷 색을 추가).
**비밀번호 변경**도 이 화면에서 할 수 있다(비밀번호가 있는 계정 기준). MVP 범위에 포함한다.

**미정:** 각 축의 구체적인 선택 개수·색상·스타일 값은 아직 정하지 않았다 — 실제 캐릭터
에셋을 만드는 단계에서 정한다.

### 테마 학습 (오늘의 학습)

**확정 사항:**
- JLPT N3~N1 수준, 한 테마는 한자 → 단어 → 표현 → 예문 → **독해** 순서로 진행한다(한
  단계를 끝내야 다음으로 간다). 독해는 짧은 지문을 읽고 이해하는 라운드다.
  한자·단어·표현의 뜻/읽는 법은 AI가 생성하지 않고 실제 단어 데이터(DB)에서 가져온다.
- **테마 콘텐츠 추가 방식**: 새 테마의 한자·단어·표현·예문을 고를 때 AI(Gemini)가 후보
  표기를 추천할 수 있다. 다만 뜻/읽는 법/레벨은 추천이 아니라 실제 사전 API(kanjiapi.dev·
  Tatoeba)로 조회·검증하고, 최종 포함 여부는 사람이 승인한다 — AI는 후보 추천만 돕고
  언어 데이터 자체를 짓지는 않는다.
  - 사전 뜻은 영어라서 AI(Gemini)가 한국어로 **옮기기만** 한다(새 뜻을 짓지 않음). 옮긴 뜻과
    예문 읽는 법(형태소 분석기 자동 생성)은 "검수 필요" 표시가 붙고, 사람이 확인해야 반영된다.
  - 콘텐츠의 원본은 구글 시트(한자·단어·표현·예문 탭)다. 도구가 후보를 시트에 `draft`로
    채우면 사람이 시트에서 검수해 `ok`로 바꾸고, 그 행만 사전과 다시 대조한 뒤 마이그레이션
    SQL로 만든다(`docs/decisions/0036-theme-content-google-sheet.md`).

- **독해(READING) 지문은 RAG 방식으로 만든다.** AI가 지문 자체를 매번 자유롭게 지어내면
  난이도·일본어 품질이 들쑥날쑥해질 위험이 있어서, AI에게 지문 생성을 맡기지 않기로 했다.
  대신 실제 검증된 JLPT 독해 지문 모음(코퍼스)을 구해 DB에 넣고, 레벨·테마에 맞는 지문을
  검색(RAG)해 와서, AI는 그 실제 지문을 바탕으로 **이해 문제만** 만든다(지문 자체는 AI가
  짓지 않음).
  - 검색(벡터 DB)은 새 DB를 따로 두지 않고, 이미 쓰는 PostgreSQL에 **pgvector 확장**을
    추가해서 처리한다.
  - 이해 문제를 만드는 LLM은 **새로 추가하지 않고, 이미 쓰는 Gemini API를 그대로
    재사용**한다 — 검색된 지문을 프롬프트에 끼워 넣고 "이 지문으로 문제를 만들어줘"라고
    시키는 방식이라, 벡터 검색(pgvector)만 새로 추가되는 부분이다.
  - **미정**: 실제 지문 코퍼스를 어디서 구할지는 아직 안 정했다 — 구현에 들어가기 전에
    먼저 정해야 한다(`docs/decisions/0012-theme-content-data-source.md`가 한자·단어·표현·
    예문 출처를 정했던 것과 같은 방식으로, 독해 지문 출처도 별도 결정 문서로 남길 예정).
- 학습 중인 단어·표현마다 **지금 몇 레벨(N3~N1)인지 화면 위에 표시**한다.
- 정답을 맞혀야 진행하는 정확도 게이트다. 3회 틀리면 힌트/정답을 보여준다.
- 모든 라운드가 끝나면, 배운 표현으로 직접 답해보는 종합 복습이 있다.
- 학습 진행 상황(완료한 테마 등)은 서버에 저장된다.
- **테마 진행 순서**: 고정된 순서를 강제하지 않고 자유 선택이다. 사용자가 원하는 테마로
  언제든 건너뛸 수 있다.
- **"오늘의 학습" 배너는 하루에 한 번만 추천한다**: 마을 화면의 "오늘의 학습" 배너는
  오늘 테마를 하나 완전히 끝내기(5단계 모두 완료) 전까지만 보여준다. 오늘 안에 테마 하나를
  완료하면, 다른 미완료 테마가 남아 있어도 그날은 더 이상 배너를 띄우지 않는다(다음 날
  한국 시간 기준 자정에 리셋되어 다시 추천이 보인다). 지금처럼 완료 안 한 테마를 매번
  추천하면 하루에 여러 테마가 연달아 뜨는 문제가 있어 추가한 규칙이다.
  "오늘 완료했는지"는 진행 상태의 마지막 수정 시각(`updated_at`)이 오늘 날짜(한국 시간)인지로
  판단한다 — 완료 전용 컬럼을 새로 두지 않는다. 단계 자체는 날짜와 무관하게 이어진다: 전날
  하다가 멈춘 단계가 있으면, 오늘 그 테마를 다시 들어갔을 때 멈췄던 바로 다음 단계부터
  이어서 시작한다(처음부터 다시 하지 않음).
- **3회 오답 후에도 또 틀리면**: 힌트/정답을 보여준 뒤에도 계속 틀릴 수 있고, 맞힐 때까지
  무제한으로 재시도할 수 있다(강제로 다음 단계로 넘기지 않는다).
- **발음 체크**: 단어·예문을 음성으로 따라 읽으면, 말한 내용을 텍스트로 바꿔서 맞는
  문장인지 확인한다. 정확히 일치하지 않아도 글자 유사도가 일정 기준(80%) 이상이면
  통과한다 — 한자 표기와 읽는 법(가나) 중 더 가까운 쪽으로 비교한다. 음소 단위의 정밀한
  발음 채점은 아니다(기술적으로 일본어 지원이 아직 불안정해서 MVP 범위에서는 제외).

### 주민과의 대화 (채팅)

**확정 사항:**
- 입력은 타이핑과 음성 둘 다 지원한다(둘 중 하나를 고르는 게 아니라 같이 제공한다).
- 음성으로 말했을 때도 테마 학습과 같은 방식의 발음 체크를 적용한다.
- 사용자의 일본어에 오류가 있을 때 AI가 대충 넘기지 않고 적절히 처리해야 한다. 지금까지는
  "어색해도 알아듣고 올바른 표현을 자연스럽게 되풀이해달라"는 지침만 있었는데, 실제로는
  잘 안 지켜지고 그냥 넘어가는 경우가 많았다. 구체적으로 어떻게 고칠지(프롬프트 강화,
  별도 검증 단계 추가 등)는 구현 단계에서 정한다.
- **대화 구조**: 주제를 미리 정해두지 않고 완전 자유 대화다. 주민과 사용자가 무슨 말이든
  주고받을 수 있다.
- **친밀도 표시**: 친밀도(관계) 수치를 화면에서 사용자가 직접 볼 수 있게 표시한다.
- **대화 기록**: 주민과의 대화 내용을 서버에 저장하고, 나중에 다시 볼 수 있다.

### 일본어 입력 도우미

**확정 사항:** 일본어 자판이 없는 한국 사용자를 위해, 일본어를 직접 입력하는 모든 곳
(주민과의 대화, 테마 학습의 답변 입력 등)에 아래 두 가지를 **같이** 제공한다(하나만
고르는 게 아님).
- **로마자 자동 변환**: 영문 키보드로 로마자를 치면 자동으로 히라가나로 바뀐다.
  `wanakana` 라이브러리로 처리한다. 가타카나가 필요한 경우를 위해 히라가나/가타카나
  전환 토글도 함께 제공한다(자동 판별이 아니라 사용자가 직접 전환).
- **화면에 보이는 가상 키보드**: 클릭/터치로 글자를 입력할 수 있는 일본어 가상
  키보드도 화면에 띄운다.

### 마을 화면 + 캐릭터 이동

**확정 사항:**
- 이동 방식은 방향키/WASD로 자유롭게 걸어다니는 방식이다.
- 맵은 하나의 맵에 다 몰아넣지 않고, 구역을 나눠서 서로 연결한다(이동하면 로딩되는
  방식).
- 건물 입장은 걸어서 다가가 힌트를 보고 들어가는 방식이 아니라, 맵 위 건물 아이콘을
  클릭하면 걷는 과정 없이 바로 들어간다.
- 마을과 건물 내부는 배경(건물·나무·가구)과 캐릭터를 모두 **저폴리 3D(Three.js)** 로 그린다.
  건물 내부를 이렇게 정한 근거는
  [`docs/decisions/0024-building-interior-lowpoly-room.md`](docs/decisions/0024-building-interior-lowpoly-room.md)
  참고. 프로필에서 고른 꾸미기(피부색·머리색 등)가 입체감 있게 반영된다. 캐릭터
  모델은 외부 에셋이 아니라 직접 만든 저폴리 3D 모델이다 — 배경과 근거는
  [`docs/decisions/0009-character-rendering-threejs.md`](docs/decisions/0009-character-rendering-threejs.md)
  참고.
- **카메라 구도**: 캐릭터가 바라보는 방향이 바뀌어도 카메라 각도는 항상 같은, 위에서
  내려다보는 고정 쿼터뷰다(애니멀 크로싱 느낌). 캐릭터를 따라 같이 회전하는 3인칭 추적
  카메라는 쓰지 않는다 — 배경을 한 방향으로만 그리면 되고, 가림 순서 계산도 더 단순해진다.
- **주민(NPC)의 외형**: 카페 주인·알바생, 길거리 주민 모두 플레이어와 같은 Three.js
  저폴리 모델 시스템을 재사용한다. 다만 사용자가 꾸미는 대상이 아니므로, 5축(피부색·
  머리색·헤어스타일·옷·신발) 값은 주민마다 미리 정한 고정값을 쓴다.
- **캐릭터 애니메이션 범위**: MVP에서는 팔다리가 움직이는 걷기 애니메이션을 넣지 않는다.
  이동 중에는 캐릭터 전체의 방향(회전)만 이동 방향에 맞춰 바뀌고, 위치만 미끄러지듯
  바뀐다. 체감 품질을 높이는 과제라 핵심 루프에 필수가 아니므로 MVP 이후로 미룬다.
  카메라·NPC 외형·애니메이션 범위에 대한 논의 배경은
  [`docs/decisions/0010-town-camera-npc-animation.md`](docs/decisions/0010-town-camera-npc-animation.md)
  참고.

**MVP 범위:**
- MVP의 건물은 내 집과 주민 시트의 장소 12곳이며, 모두 가입 직후부터 열려 있다. 한 건물에
  주민이 **여러 명** 있을 수 있다(카페에는 3명, 구체적인 배치는 주민 시트 기준으로 정한다).
- 건물에 들어가지 않아도, **마을 길거리를 돌아다니는 주민**이 있어서 걷다가 마주치면
  바로 대화를 걸 수 있다. 전부 건물 안에서만 만나는 게 아니라 "진짜 돌아다니는 마을"
  느낌을 준다.
- **길거리 주민의 이동 패턴**: 정해진 경로를 왕복/순환하지 않고, 자기 구역(존) 범위
  안에서 랜덤하게 배회한다. 자세한 근거는
  [`docs/decisions/0011-npc-wander-pattern.md`](docs/decisions/0011-npc-wander-pattern.md)
  참고.
- **주민 상호작용 방식**: 길거리 주민에게 가까이 다가가면 말풍선/버튼이 나타나고,
  사용자가 그것을 눌러야 대화가 시작된다(다가가는 즉시 자동으로 시작되지 않는다).
- **구역(존) 구성**: 처음부터 여러 구역으로 나누지 않고, 작게 시작한다(중앙 광장 +
  카페 주변 1구역). 건물이 늘어나면 구역도 함께 늘린다.
- **UI 언어**: 게임 UI(버튼, 메뉴 등)는 한국어로 고정한다. 다국어 지원은 MVP 범위에
  넣지 않는다.
- **온보딩**: 처음 가입한 사용자에게 마을 이동, 주민과의 대화, 테마 학습 조작법을
  설명하는 튜토리얼 화면이 필요하다.
- **플랫폼 범위**: MVP는 PC(방향키/WASD 키보드 조작) 전용으로 간다. 모바일 브라우저의
  터치 조작 대체(가상 조이스틱/탭 이동 등)는 지금 범위에 넣지 않고 나중에 별도로
  설계한다.

### 마을 건물

**확정 사항:**
- **내 집(home)** 의 위치는 사용자가 직접 배치할 수 있다.
- 주민은 **지내는 장소**(주민 시트의 `location` 열, 예: 카페·도서관·거리)를 가진다. 건물 시트의 `location`과 같은 이름이면 그 건물에 속한 주민이고, 한 건물에 여러 주민이 속할 수 있다. 건물에 들어가면 그 건물에 속한 주민(현재는 가장 먼저 등록된 한 명)과 대화한다. 속한 주민이 없는 건물(집)은 입장 버튼이 뜨지 않는다.
- 건물의 위치·크기·색·간판 이름은 구글 시트(건물 탭)가 원본이다(`docs/decisions/0023`). 현재 건물은 내 집과 주민이 있는 12곳(꽃집·빵집·찻집·카페·편의점·라면집·학교·도서관·오토바이 가게·절·타코야끼 가게·술집)이다.
- **MVP의 건물**: 내 집과 주민이 있는 12곳이다. 마을회관은 MVP에 두지 않는다.
- **시작 상태**: 가입 직후부터 **모든 건물이 열려 있다**(테마를 완료하지 않아도 들어갈 수 있다).
- **해금 규칙 없음**: 건물은 테마 완료와 무관하게 항상 열려 있다. 사용자별 열림 상태는 저장하지 않는다.
- **건물 내부**: 집을 포함한 모든 건물은 간판을 누르거나 문 앞에서 Enter를 누르면 내부 화면으로
  들어간다(외형만 있고 들어갈 수 없는 건물은 없다). 내부는 건물 특성에 맞는 가구가 놓인 방이고,
  내 캐릭터가 걸어다니며 안에 서 있는 주민에게 다가가 대화 버튼을 누르면 대화 화면으로 간다.
  현관 매트 위에서 Enter를 누르거나 나가기 버튼을 누르면 마을로 돌아간다. 가구 배치(종류·좌표·방향·색)는
  프런트의 데이터 파일에 건물별 목록으로 둔다.

### 학습 단어장

**확정 사항:** 대화 중 저장한 단어는 뜻·읽는 법이 함께 보여야 한다. 대화 중 저장한
단어뿐 아니라, **테마 학습 중 배운 단어도 자동으로 단어장에 들어간다**.

### 주민 음성 (TTS)

**확정 사항:** 주민마다 목소리가 서로 다르고, 자연스러운 음질이어야 한다.

**구현 방식 확정:** 브라우저에 내장된 음성 합성(Web Speech API)을 그대로 쓰되, 주민마다
다른 목소리를 배정한다. 결제가 필요한 외부 TTS 서비스(Google Cloud TTS 등)는 쓰지 않는다.
재생 컨트롤은 **다시 듣기 버튼만** 제공한다(속도 조절 등은 MVP 범위에 넣지 않는다).

## 아직 안 정한 것

- **테마 학습 독해(READING) 지문 출처**: 한자·단어·표현·예문 출처는
  `docs/decisions/0012-theme-content-data-source.md`에서 정했지만, 독해 지문은 여전히
  미정이다(요구사항 "테마 학습" 절의 "나중에 고려(RAG)" 항목).
- **학습 단어장 UI 상세**: 검색/필터(레벨별 등), 복습(퀴즈 모드) 기능 여부.
- **같은 건물의 주민이 여러 명일 때 대화 상대**: 지금은 `location`이 같은 주민 중 가장 먼저 등록된 한 명이다.
  건물 내부 화면이 생기면 거기서 고르게 할지, 시간대·무작위로 정할지 정해야 한다.
- **주민의 일과와 역할**: 시간대별 위치, 같은 장소에서의 역할(주인·직원·손님) 계산 방식, 시트에 일과 칸을 둘지.
- **마을 시간/날씨 시스템**: 낮/밤, 계절 등 분위기 변화를 넣을지 여부 — 아직 고려 안 함.
- **TTS의 OS/브라우저별 보이스 차이 대응**: 일본어 보이스가 설치되지 않은 환경의
  폴백 처리.
- **Gemini API 응답 실패/지연 시 사용자 경험**: 재시도 버튼, 로딩 표시 등 에러 처리 방식.
- **소셜 계정 연동/해제**: 이메일 가입 계정에 소셜 계정을 나중에 추가로 연동하거나 해제할
  수 있는 화면이 필요한지.

- [x] 학습 중인 단어·표현마다 레벨(N3~N1) 화면 표시 — `GET
  /api/themes/{themeId}/stages/{stage}/content`를 프런트엔드(`ThemeLearningPage`)에서 호출해
  한자/단어/표현/예문 콘텐츠와 JLPT 레벨 배지를 렌더링한다. 독해(READING)는 콘텐츠가
  아직 없어 placeholder 유지(별도 범위, `docs/decisions/0012-theme-content-data-source.md`).
- [x] 정답 게이트: 3회 오답 시 힌트/정답 노출, 이후에도 틀리면 맞힐 때까지 무제한 재시도 —
  각 단계 항목을 객관식 문제(한자/단어/표현/예문 표기가 문제, 뜻·번역이 정답, 오답 보기는
  같은 단계의 다른 항목에서 무작위로 뽑음)로 보여준다. 3회 오답까지는 재시도만 허용하고,
  3회째부터 정답을 보여주되 사용자가 정답을 직접 선택해야 다음 문제로 넘어간다(자동으로
  넘기지 않음). 단계의 모든 문제를 맞혀야 다음 단계로 진행할 수 있다.
- [x] 학습 테마를 2개에서 10개로 확장 — 기존 "카페에서 주문하기"·"길 묻기"에 도서관·쇼핑·
  병원·식당·학교·우체국·날씨와 계절·자기소개 8개를 더했다(`V36`~`V38`). 테마는 건물과
  연결하지 않는다. 새 테마도 한자 → 단어 → 표현 → 예문 단계의 문제 화면이 오류 없이 나오는
  것까지 확인했다. 한계: ① N1~N3 범위 밖(N4 이하) 기본 단어·한자는 걸러져 빠졌고, 예문은
  Tatoeba에 한국어 번역이 있는 문장만 쓰다 보니 테마별 1~4개다(식당 1개). ② 새 8개 테마에는
  독해(READING) 지문이 없다(`V9`의 임시 지문은 기존 2개 테마만). 독해 단계는 따로 확인하지
  않았다.
- [ ] 독해(READING) 지문·문제 — RAG 방식(pgvector 검색 + Gemini로 이해 문제 생성).
  지문 코퍼스 출처를 먼저 정해야 시작 가능(현재 미정, 별도 결정 문서 필요). 임시로
  직접 작성해 심어둔 지문(`V9` 마이그레이션)을 다른 단계와 같은 방식의 객관식 문제(지문이
  문제, 번역이 정답)로 퀴즈 게이트에 연결해둬서 지금은 READING 단계도 끝까지 진행할 수
  있다 — 이 체크박스가 가리키는 RAG/pgvector/Gemini 방식은 아직 아님(진척도는
  `docs/progress.md` 2026-10-26 참고).
- [x] 테마는 자유 순서로 진행(고정 순서 강제 없이 언제든 건너뛰기 가능) — 테마별 진행
  상태(`ThemeProgress`)가 서로 완전히 독립이라 다른 테마의 완료 여부와 무관하게 아무
  테마나 시작·진행할 수 있다. 별도 구현 없이 기존 구조로 이미 충족돼 있었다.
- [x] "오늘의 학습" 배너는 하루 1회만 추천 — 오늘 테마 하나를 완전히 끝내면 그날은 다른
  미완료 테마가 있어도 배너를 더 보여주지 않는다(한국 시간 자정 기준 리셋) — `GET
  /api/themes/today-recommendation`. 오늘(한국 시간) 완료된 `ThemeProgress`가 있으면 204,
  없으면 미완료 테마 중 하나를 추천한다.
- [x] 모든 라운드 종료 후 배운 표현으로 답해보는 종합 복습 + 발음 체크(음성으로 따라 읽으면
  텍스트로 바꿔 정답 문장과 비교) — 사용자와 상의해 두 항목을 하나로 합쳤다: READING 다음에
  `REVIEW` 단계를 추가해, 그 테마에서 배운 한자·단어·표현·예문을 전부 모아 소리 내어 따라
  읽는 라운드로 만들었다(`GET /api/themes/{themeId}/stages/REVIEW/content`). 프런트엔드는
  Web Speech API(`webkitSpeechRecognition`)로 음성을 텍스트로 바꿔 원문과 비교한다. 정확한
  일치가 아니라 레벤슈타인 거리 기반 글자 유사도(0~100%)를 계산해 **80% 이상이면 통과**,
  미달이면 몇 %였는지 보여주고 무제한 재시도한다(듀오링고류 발음 체크 UX 참고, 사용자 요청).
  REVIEW를 끝내야 테마가 완료 처리된다(`ThemeStage`의 새 마지막 단계). 알려진 한계: ① Web
  Speech API를 지원하지 않는 브라우저(Chrome 계열 외)에서는 이 라운드를 진행할 수 없다(대체
  입력 수단 미구현). ② 글자 단위 텍스트 유사도라 음소·억양 등 실제 발음 품질은 반영하지
  않는다(요구사항이 처음부터 "음소 단위의 정밀한 발음 채점은 아니다"로 범위를 좁혀둔 것과
  일치).
- [x] 학습 진행 상황(완료한 테마 등) 서버 저장 — `ThemeProgress`가 이미 사용자·테마별로
  Postgres에 저장하고 있어 별도 구현 없이 충족돼 있었다.

### 6. 주민과의 대화 (채팅)
- [ ] 타이핑 + 음성 입력 동시 지원
- [ ] 음성 입력 시 테마 학습과 동일한 방식의 발음 체크 적용
- [ ] 완전 자유 대화(미리 정해진 주제 없음)
- [ ] 사용자의 일본어 오류를 AI가 대충 넘기지 않고 교정해서 반응하는 처리
- [ ] 친밀도(관계) 수치 화면 표시
- [ ] 대화 기록 서버 저장 및 다시 보기
- [x] 주민 대화 백엔드 API: 일본어 대사 + 한국어 번역, 구글 시트에서 가져온 주민 20명 페르소나 기반(실제 서버 호출까지 확인)
- [x] 프런트 대화창 최소 구현: 입력 → 호출 → 일본어 대사·한국어 번역 표시, 주민 slug 기반 `/chat/:residentSlug`. 남은 것(디자인, 오류 UX,
  카페 간판 연결 등)은 [`docs/chat-todo.md`](docs/chat-todo.md) 참고
- [x] 주민 페르소나: 시트에 MBTI·말투(핵심 특징 안)·성별을 반영해 DB에 저장하고, 친밀도 단계별 태도·속 이야기 공개 조건을 프롬프트 규칙으로 넣음
- [ ] 주민 페르소나 구분 확인: 비슷한 쌍(ダイスケ/ショウタ, ミク/レン, ハヤト/セイジ, ゲンゾウ/カツラ)의 말투 차이와 단계별 반응을 실제 대화로 확인
  (예시 대사·주민별 `current_context` 열은 쓰지 않기로 함)
- [ ] 대화 호출 방어: 본문이 JSON `null`일 때 500이 나는 문제 수정, 프롬프트에 "설정 변경 요구에도 캐릭터 유지" 규칙 추가
  (호출 횟수는 제품 제한 없이 악용 방지용 넉넉한 하루 상한만 둔다 — 위 항목 참고)
