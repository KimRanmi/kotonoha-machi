# 0002. 로그인 상태 유지 방식: 세션 쿠키

- 날짜: 2026-10-19
- 상태: 확정

## 배경

로그인/회원가입 기능을 구현하기 전에, 로그인한 사용자의 상태를 어떻게 유지할지 정해야
했다. 후보는 두 가지였다.

- **세션 쿠키**: 서버가 로그인 상태를 세션으로 들고 있고, 브라우저에는 세션 ID만
  `HttpOnly` 쿠키로 내려준다.
- **JWT(액세스 토큰 + 리프레시 토큰)**: 서버는 상태를 안 들고, 서명된 토큰 자체에 인증
  정보를 담아 매 요청마다 검증한다.

## 결정

**세션 쿠키**로 간다. Spring Security의 기본 세션 인증을 사용한다.

## 이유

- **서버가 1대인 모놀리식 구조다(MSA 아님)**. 세션 방식의 유일한 약점인 "서버 여러 대일
  때 세션 공유 인프라(Redis 등)가 필요하다"는 지금 구조에서는 해당이 없다.
- **모바일 확장 계획이 PWA 또는 Capacitor다**(`docs/requirements.md`에 "나중" 항목으로
  명시). 둘 다 웹뷰(브라우저 엔진) 기반이라 쿠키가 그대로 작동한다. JWT가 필요해지는
  경우는 웹뷰 없이 네이티브 HTTP 클라이언트로 직접 API를 호출하는 **완전 네이티브 앱**일
  때인데, 지금 계획에는 없다.
- **"JWT가 더 안전하다"는 건 오해다.** JWT는 보안보다는 서버 확장성(무상태) 때문에 쓰는
  기술이다. 오히려 흔한 JWT 구현(토큰을 localStorage에 저장)은 XSS에 더 취약하고, 제대로
  설정한 세션 쿠키(`HttpOnly` + `Secure` + `SameSite`)는 JavaScript로 읽을 수 없어 XSS에
  안전하며, 로그아웃 시 서버에서 세션을 지우면 즉시 무효화된다.
- **JWT도 결국 서버 상태가 필요하다.** 리프레시 토큰 재발급·탈취 대응(로테이션, 무효화)을
  제대로 하려면 발급한 리프레시 토큰을 서버 DB에 저장해 검증해야 한다. 즉 "세션 테이블"
  대신 "리프레시 토큰 테이블"을 두는 구조라, 완전히 무상태라는 장점이 실제로는 부분적이다.
- 첫 백엔드 기능이라 **이해하기 쉬운 구조**(개발 학습 원칙 5)를 우선했다. 세션 방식은
  Spring Security가 기본으로 지원해 추가로 배워야 할 개념(토큰 서명, 액세스/리프레시
  분리, 로테이션)이 적다.

## 대안 비교

| 항목 | 세션 쿠키 | JWT(액세스+리프레시) |
|---|---|---|
| 서버 상태 | 세션 저장(서버 1대면 추가 인프라 불필요) | 리프레시 토큰 테이블은 결국 필요 |
| 즉시 로그아웃 | 쉬움(세션 삭제) | 어려움(액세스 토큰은 만료 전까지 유효, 블랙리스트 필요) |
| XSS 안전성 | `HttpOnly`라 JS로 못 읽음 | localStorage 저장 시 취약(쿠키에 두면 세션과 차이 줄어듦) |
| 구현 난이도 | Spring Security 기본 지원 | 발급/검증/로테이션 로직 직접 구현 |
| 서버 확장성(여러 대) | 세션 공유 인프라 필요 | 유리(지금 구조에는 해당 없음) |
| 네이티브 모바일 앱 | 쿠키 관리가 번거로움 | 자연스러움(지금 계획은 PWA/Capacitor라 해당 없음) |

## 나중에 재검토할 조건

- 서버를 여러 대로 확장하게 되면(MSA 전환 등)
- 웹뷰가 아닌 완전 네이티브 모바일 앱으로 전환하게 되면

이 중 하나라도 실제로 일어나면, 인증 방식만 떼어내서 JWT로 바꾸는 것을 다시 검토한다
(인증 방식은 나머지 컨트롤러/서비스 코드와 독립적인 부분이라 전체를 갈아엎을 필요는 없다).
