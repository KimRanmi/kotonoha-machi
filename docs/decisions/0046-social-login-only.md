# 0046. 이메일 가입·비밀번호 기능 제거, 소셜 로그인만 지원

- 날짜: 2026-11-23
- 상태: 확정(구현 완료, 운영 배포는 머지 후)

## 배경

도메인을 사 두지 않고 GCP VM의 IP로 배포하는 상태라 Resend로 이메일을 보낼 수 없다.
Resend는 도메인 인증 전에는 본인 계정 이메일로만 발송할 수 있어서([0005](0005-email-sending.md)),
이메일 인증 코드가 필요한 회원가입과 비밀번호 재설정이 운영에서 동작하지 않는다. 소셜 로그인(구글·카카오·네이버)은
이미 있고, 제공자가 이메일 소유를 확인해 주므로 이메일 인증이 따로 필요 없다.

## 결정

소셜 로그인만 남기고 아래를 모두 제거한다.

- 백엔드: 회원가입·닉네임 중복 확인(가입 폼용)·이메일 인증·인증 코드 재전송, 이메일/비밀번호 로그인(로그인 실패 횟수 잠금 포함),
  비밀번호 재설정·변경, `EmailSender`/`ResendEmailSender`, `resend-java` 의존성, `RESEND_API_KEY`·`EMAIL_FROM_ADDRESS` 설정,
  `PasswordVerifier`, `AuthUserDetails`/`CustomUserDetailsService`, 비밀번호 인코더·`AuthenticationManager` 빈.
- 프런트엔드: 가입 화면, 비밀번호 재설정 화면, 로그인 화면의 이메일/비밀번호 폼, 프로필의 비밀번호 변경, 탈퇴 시 비밀번호 확인.
- 회원 탈퇴(`DELETE /api/auth/me`)는 비밀번호 재확인 없이 본문 없이 호출한다.

## 일부러 남긴 것

- **DB 컬럼**: `password_hash`, `verification_*`, `login_fail_count`, `locked_until`, `password_reset_*`은 그대로 둔다(새 마이그레이션 없음).
  운영 DB 데이터를 건드리지 않기 위해서다. `User` 엔티티는 이 컬럼들을 더 이상 매핑하지 않는다(나머지 NOT NULL 컬럼은 DB 기본값 0이 있다).
- **`UserStatus.PENDING_VERIFICATION`**: 예전에 인증을 끝내지 못한 계정 행을 읽어야 해서 유지한다.
- **기존 비밀번호 계정**: 같은 이메일로 소셜 로그인하면 기존 계정에 자동 연결되므로 계속 쓸 수 있다
  (`CustomOAuth2UserService`가 이메일로 연결). 다만 소셜 제공자가 그 이메일을 주지 않는 경우(예: 카카오 이메일 미동의)는 로그인할 수 없다.

## 영향과 한계

- 로그인 수단이 소셜 제공자에 전적으로 의존한다. 제공자 콘솔의 리디렉션 URI 설정이 운영 주소와 맞아야 한다.
- 나중에 도메인을 사서 이메일을 다시 쓰고 싶으면 이 변경을 되돌리는 것이 아니라 새로 설계한다.
- 테스트는 소셜 로그인을 실제로 호출할 수 없어서, 소셜 로그인 성공 시 세션에 남는 인증 정보를 세션에 직접 넣는
  `TestSessions` 헬퍼로 로그인한 상태를 만든다.
