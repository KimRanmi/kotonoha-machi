# 0005. 이메일 인증 코드 발송: Resend

- 날짜: 2026-10-21
- 상태: 폐기됨 — [0046](0046-social-login-only.md)에서 이메일 발송 자체를 없앴다(아래는 당시 기록)

## 배경

회원가입 시 이메일 인증 코드를 발송해야 하는데, 지금까지는 `LogEmailSender`로 실제
발송 없이 서버 로그에만 코드를 찍고 있었다. 실제 이메일을 보내는 구현체로 교체하기
위해 후보를 비교했다.

- **Gmail SMTP**: 이전에 다른 프로젝트에서 써본 방식. 이번엔 다른 서비스를 써보고
  싶어서 제외.
- **SendGrid**: 2025-05-27부로 영구 무료 플랜이 폐지되고, 가입 시 60일 트라이얼(일
  100건)만 제공한 뒤 유료 전환이 필요하다.
- **AWS SES**: 계정이 이미 있지만 12개월 무료 티어가 끝난 상태라 과금 가능성이
  생긴다. 또한 신규 계정은 기본적으로 샌드박스 모드라 인증된 수신자에게만 발송
  가능하고, 임의의 가입자 이메일로 보내려면 AWS Support에 프로덕션 액세스를
  요청해 승인을 기다려야 한다. 포트폴리오 관점에서는(클라우드 인프라 경험 어필)
  AWS 쪽이 유리하지만, 신용카드가 연결된 계정에 과금 리스크를 안고 싶지 않다는
  판단이 더 우선했다.
- **Resend**: 무료 티어가 기간 제한 없이 유지되고(월 3,000건/일 100건), 가입에
  신용카드가 필요 없다. REST API 방식이라 SMTP와 다른 연동 방식을 경험할 수 있다.

## 결정

**Resend**로 간다. 백엔드에 `com.resend:resend-java` SDK를 추가하고,
`EmailSender` 인터페이스의 구현체를 `LogEmailSender`에서 `ResendEmailSender`로
완전히 교체한다(로그 출력 방식은 남겨두지 않는다).

## 이유

- 과금 리스크가 구조적으로 없다 — 무료 티어에 기간 제한이 없고 카드 등록도
  필요 없어서, 개인 프로젝트에서 "실수로 요금이 발생할까" 하는 걱정을 안 해도 된다.
- 설정 난이도가 낮다 — 도메인 인증은 DNS에 SPF/DKIM 레코드만 추가하면 되고, AWS
  SES처럼 별도 승인 절차(프로덕션 액세스 요청)가 없다.
- `EmailSender` 인터페이스로 이미 추상화돼 있어서, 구현체 교체가 `AuthService`나
  테스트 코드(`EmailSender`를 `MockitoBean`으로 대체)에 영향을 주지 않는다.

## 대안 비교

| 항목 | Gmail SMTP | SendGrid | AWS SES | Resend |
|---|---|---|---|---|
| 무료 티어 | 개인 계정 한도 내 | 60일 트라이얼만(영구 무료 폐지) | 12개월 한정(이미 소진) | 기간 제한 없음(월 3,000건) |
| 카드 등록 | 불필요 | 필요 | 필요 | 불필요 |
| 임의 수신자 발송 | 바로 가능 | 바로 가능 | 승인 전까지 인증된 수신자만 | 도메인 인증 전까지 본인 계정 이메일만 |
| 연동 방식 | SMTP | REST API | REST API/SMTP | REST API |
| 포트폴리오 인지도 | 낮음 | 보통(업계에서 알려짐) | 높음(클라우드 인프라 경험 어필) | 낮음(비교적 신생) |

## 한계와 재검토 조건

- 지금은 Resend의 공용 테스트 도메인(`onboarding@resend.dev`)으로 발송하는데, 이
  상태에서는 **Resend 계정 소유자 본인 이메일로만** 발송이 성공한다. 실제 가입자
  누구에게나 보내려면 직접 소유한 도메인을 추가하고 SPF/DKIM 레코드로 인증해야
  한다(배포 전에는 반드시 해야 할 일).
- 월 3,000건/일 100건을 넘는 트래픽이 생기면 유료 전환을 검토한다.
