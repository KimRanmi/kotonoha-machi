# 0006. 회원 탈퇴 처리 방식: 소프트 삭제(상태 변경)

- 날짜: 2026-10-21
- 상태: 확정

## 배경

프로필 화면에 회원 탈퇴 기능을 추가하면서, 탈퇴한 계정의 데이터를 어떻게 처리할지
정해야 했다. 후보는 두 가지였다.

- **하드 삭제**: `users` 행을 바로 지운다. 연결된 `social_accounts`도 FK cascade로
  같이 지워진다.
- **소프트 삭제**: `UserStatus`에 `WITHDRAWN` 상태를 추가하고, 탈퇴 시 행은 그대로
  두고 상태만 바꾼다.

지금 시점에는 `user`를 참조하는 다른 도메인 테이블이 전혀 없어(chat/town/resident/
theme/vocabulary 패키지는 아직 빈 패키지), 하드 삭제가 더 단순했다. 하지만 사용자가
탈퇴 통계·악용 방지(탈퇴 후 재가입 패턴 등) 같은 이유로 데이터 보존이 유리한 소프트
삭제를 선택했다.

## 결정

**소프트 삭제**로 간다. `UserStatus.WITHDRAWN`을 추가하고, 탈퇴 시 `users` 행은
삭제하지 않고 상태만 바꾼다. 이메일·닉네임은 익명화하지 않는다(행을 그대로 보존하는
것이 목적이라, 바로 다음 절의 한계를 감수한다).

## 적용 범위

- **비밀번호 로그인 차단**: `AuthUserDetails.isEnabled()`가 이미 `status == ACTIVE`만
  허용하므로, `WITHDRAWN`도 자동으로 로그인이 막힌다(추가 변경 불필요).
- **소셜 로그인 차단**: `CustomOAuth2UserService`는 `UserDetailsService` 경로를 타지
  않아 `isEnabled()` 검사를 거치지 않는다. 탈퇴한 계정에 연결된 소셜 계정으로 로그인을
  시도하면 상태를 직접 확인해 거부하도록 `resolveUser`에 분기를 추가해야 한다.
- **탈퇴 처리**: 비밀번호가 있는 계정은 현재 비밀번호 재확인 후 탈퇴, 소셜 전용 계정은
  재확인 없이 탈퇴 처리한다. 탈퇴 후 세션을 즉시 무효화(로그아웃)한다.

## 한계 (알고 있는 트레이드오프)

- 이메일·닉네임을 익명화하지 않으므로, 탈퇴한 계정의 이메일/닉네임으로는 **다시 가입할
  수 없다**(`UserRepository`의 unique 제약이 행 자체에 걸려 있기 때문). 재가입을
  지원하려면 익명화(예: 이메일을 `withdrawn-{id}@...` 형태로 바꾸는 등) 또는 재활성화
  플로우가 추가로 필요하다 — 지금은 범위에 넣지 않는다.
- 나중에 채팅 로그·학습 기록처럼 `user_id`를 참조하는 테이블이 생기면, 그 테이블들의
  탈퇴 계정 데이터를 어떻게 할지(보존/익명화/삭제)를 각 기능 구현 시점에 다시 정해야
  한다. 이번 결정은 "계정 자체"에만 적용된다.
- 탈퇴 처리는 탈퇴 요청을 보낸 "현재 세션"만 무효화한다. 같은 계정으로 이미 로그인된
  다른 기기·브라우저의 세션은 각 세션이 만료되기 전까지는 계속 동작한다. 이는 앱
  전체에 `SessionRegistry` 같은 동시 세션 관리 체계가 없는 기존 아키텍처의 한계이며,
  이번 탈퇴 기능이 새로 만든 문제는 아니다.

## 나중에 재검토할 조건

- 탈퇴한 이메일로 재가입을 허용해야 하는 요구사항이 생기면, 익명화 또는 재활성화 플로우를
  추가로 설계한다.
