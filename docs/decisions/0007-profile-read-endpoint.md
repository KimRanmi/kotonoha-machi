# 0007. 프로필 화면의 조회 API: `/api/auth/me` 재사용 대신 `user` 도메인에 전용 엔드포인트 추가

- 날짜: 2026-10-21
- 상태: 확정

## 배경

프로필 화면(이메일/닉네임 조회 + 닉네임 수정)을 만들면서, 화면에 보여줄 조회 API를 어디서
가져올지 정해야 했다. 이미 `GET /api/auth/me`(`AuthController`)가 로그인한 사용자의
id/email/nickname을 돌려주고 있어서, 응답 모양이 지금 당장 필요한 정보와 완전히 같았다.

후보는 두 가지였다.

- **재사용**: 프런트엔드 `ProfilePage`가 기존 `/api/auth/me`를 그대로 호출한다. 백엔드
  변경이 전혀 없다.
- **전용 엔드포인트 추가**: `user` 도메인에 `GET /api/users/me`를 새로 만들고, 프로필
  화면은 이 엔드포인트를 쓴다. `/api/auth/me`는 그대로 두고 건드리지 않는다.

## 결정

**전용 엔드포인트를 추가**한다. `user/controller/ProfileController`에 `GET /api/users/me`
(조회)와 `PATCH /api/users/me/nickname`(닉네임 변경)을 함께 둔다.

## 이유

- **역할이 다르다.** `/api/auth/me`는 "지금 로그인이 되어 있는가/누구인가"를 확인하는
  인증 도메인의 기능이다(`ProtectedRoute`가 라우트 가드로 쓰는 용도). 반면 프로필 화면이
  필요한 건 "내 계정 데이터를 보여주고 수정한다"는 user 도메인의 기능이다. 지금은 두 응답이
  우연히 같은 필드(id/email/nickname)를 돌려주지만, 그건 이 두 기능이 같다는 뜻이 아니라
  아직 user 도메인에 조회용 데이터가 nickname/email 말고는 없다는 뜻이다.
- **이미 user 패키지가 이 책임을 선언하고 있었다.** `user/package-info.java`에 "프로필(닉네임
  수정, 캐릭터 꾸미기)을 담당한다"고 이미 적혀 있다. 조회를 auth 쪽에 맡겨두면 "프로필 조회는
  auth가, 수정은 user가" 하는 식으로 같은 화면의 책임이 패키지 경계를 가로질러 쪼개진다.
- **곧 벌어질 변경에 대비한다.** `docs/requirements.md`의 "프로필" 절에 비밀번호 유무,
  소셜 연동 상태, 캐릭터 꾸미기(아바타) 같은 필드가 이후 작업으로 이미 예정돼 있다. 이
  정보는 전부 user 도메인 데이터라 `/api/auth/me`의 응답에 넣는 게 자연스럽지 않다(인증
  목적의 엔드포인트가 점점 프로필 화면 전용 데이터로 비대해진다). 지금 user 도메인에 조회
  엔드포인트를 만들어두면, 다음 작업(비밀번호 변경/소셜 연동)에서 같은 엔드포인트에 필드만
  늘리면 된다.
- **비용이 작다.** 새 엔드포인트가 당장 추가하는 코드는 컨트롤러 메서드 하나뿐이고(서비스
  로직 없음), `AuthController.me`와 똑같은 패턴(`AuthPrincipal.resolve` → 응답 DTO 변환)을
  그대로 재사용한다. 과도한 추상화 없이 역할 분리 이득을 얻을 수 있다.

## 적용 범위

- `/api/auth/me`는 변경하지 않는다. 로그인 필수 라우트 가드(`ProtectedRoute`)는 계속 이
  엔드포인트를 쓴다.
- `ProfilePage`는 새 `/api/users/me`, `/api/users/me/nickname`만 호출한다.

## 나중에 재검토할 조건

지금은 `/api/auth/me`와 `/api/users/me`의 응답 필드가 겹친다. 두 엔드포인트가 끝까지
겹치는 정보만 돌려주는 채로 오래 간다면(= user 도메인에 추가 필드가 전혀 안 생긴다면)
중복 엔드포인트라는 비판이 맞을 수 있다. 다음 프로필 작업(비밀번호/소셜 연동/아바타)에서
`/api/users/me`에 실제로 필드가 늘어나는지 확인한다.
