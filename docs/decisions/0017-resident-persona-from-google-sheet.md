# 0017. 주민 페르소나 데이터: 구글 시트에서 편집하고 스크립트로 Flyway SQL을 만들어 Postgres에 저장

- 날짜: 2026-11-08
- 상태: 확정 (`current_context` 처리는 임시, 아래 "남은 문제" 참고)

## 배경

주민(NPC)과의 대화는 Gemini가 주민의 성격·배경을 읽고 그 인물로 답하게 만든다. 주민이 늘어날 때마다 코드를
고치지 않고, 코드 밖(구글 시트)에서 주민을 추가·수정하고 싶다.

## 결정

```
구글 시트 → (웹 게시 CSV) → scripts/import-residents → Flyway upsert SQL → 사람이 검토 후 커밋 → Postgres → ChatService가 프롬프트 생성 → Gemini
```

- 시트는 편집 도구일 뿐이고, 서비스 중에는 읽지 않는다. 백엔드는 DB 값만 쓴다.
- 스크립트는 DB에 직접 쓰지 않고 검토용 SQL 파일(`ON CONFLICT (slug) DO UPDATE`)만 만든다. 기존 테마 콘텐츠 도구
  (`0012`)와 같은 방식이다. 시트에서 지운 주민은 DB에서 지우지 않는다.
- 시트는 웹에 게시한 CSV 주소로 읽는다(키·새 라이브러리 불필요). 주소는 `scripts/import-residents/.env`에 둔다.
- 시트 열은 `id, name, personality, appearance_job, core_features, hobby`이고, 스크립트가 `slug`(`r01`…), 괄호 안
  일본어 이름, 합친 `background`로 바꾼다. 시트 항목이 늘면 열과 변환 규칙을 함께 바꾼다.
- `{` `}`가 들어간 값은 거부하고, `ChatService`는 템플릿 치환을 한 번에 처리해 값 안의 `{…}`가 다시 치환되지
  않게 한다.

## 검토한 선택지

- **Redis 등 캐시**: 주민 테이블은 몇 줄이라 ID 조회가 사실상 즉시이고 대화의 지연은 Gemini 호출이 대부분이라 도입하지
  않았다. 새 서버·의존성이 늘어나는 비용도 있다.
- **백엔드가 시트를 실시간 조회**: 외부 호출이 대화마다 생기고, 시트 장애·오타가 서비스에 바로 영향을 줘서 제외했다.
- **스크립트가 DB에 직접 upsert**: 편하지만 검토 단계와 git 기록이 없고 DB 접속 정보가 필요해서 제외했다.

## 남은 문제

- 주민 수와 추가 방식은 상황을 보며 조정한다(처음엔 적게 시작해 늘리는 쪽을 논의했고, 시트에는 20명이 들어갔다).
- `current_context`(현재 장소/상황)는 시트에 없어서 모든 주민에게 같은 기본 문장을 넣었다. 주민이 마을을 돌아다니므로,
  나중에 대화를 시작할 때의 실제 위치로 덮어쓰는 방식을 정해야 한다. 아직 정하지 않았다.
- 시트의 나나(사서)로 기존 나나(카페 알바생)를 교체했다. 카페 주인 미유는 시트에 없어 DB에만 남아 있다. 요구사항 문서의
  "카페 주인 미유 + 알바생 나나" 문구와 어긋나므로 이후 정리가 필요하다.
