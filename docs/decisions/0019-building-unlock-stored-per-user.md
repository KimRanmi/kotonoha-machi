# 0019. 건물 해금: 사용자별로 DB에 저장하고 서버가 응답

- 날짜: 2026-11-09
- 상태: 폐기됨 (2026-11-09 건물을 해금 없이 처음부터 모두 열기로 바꾸면서 `user_building`·해금 코드를 제거했다. 아래는 당시 결정 기록)

## 배경

마을 건물(집·카페·상점)의 열림 여부가 프런트 코드의 고정 값(`locked`)이었다. 요구사항은 "카페는 완료한 테마 1개 이상,
상점은 3개 이상이면 열리고, 서버가 사용자별로 저장·응답한다"이다.

## 결정

- 열린 건물을 `user_building` 표에 사용자별로 저장한다(`user_id`, `building_id`, `unlocked_at`, 사용자+건물 조합은 유일).
  한 번 행이 생기면 유지되어 다시 잠기지 않는다.
- 규칙(집 0개, 카페 1개, 상점 3개 완료)은 `VillageBuilding` enum 한 곳에 두고 일반 코드(`VillageService`)가 판단한다.
- 테마가 완료되는 순간(`ThemeService.completeStage`) 같은 트랜잭션 안에서 `VillageService.unlockBuildings`를 호출해 조건을
  넘은 건물을 저장한다. 이미 열린 건물은 `INSERT ... ON CONFLICT DO NOTHING`이라 중복 저장되지 않는다.
- `GET /api/village/buildings`가 건물 3개(집, 카페, 상점 순)의 `{id, unlocked}`를 돌려준다.
- 프런트는 이 값을 마을 간판의 클릭·강조·"準備中" 표시에 쓴다. API가 실패하면 모든 건물을 잠금으로 본다.
- 집은 가입 경로가 이메일·소셜 두 곳이라, 가입 시점에 저장하지 않고 **조회할 때 열려야 하는데 빠진 건물(집 등)을 채우는**
  방식으로 열었다. 어떤 경로로 가입해도 집이 열리고 인증 코드를 건드리지 않는다. 대신 이 GET이 DB에 쓸 수 있다(멱등).
- 기존 사용자는 `V20` 마이그레이션이 한 번 채운다(집=가입 시각, 카페=첫 완료 테마 시각, 상점=세 번째 완료 테마 시각).

## 대안과 선택 이유

- **조회 시 완료 테마 수로 계산(별도 표 없음)**: 표가 늘지 않고 값이 어긋날 수 없다. 열린 시점도 완료 기록의 시각으로 구할 수는
  있다. 하지만 규칙이 바뀌면 이미 열린 건물이 다시 잠길 수 있어서, 요구사항 문장("서버가 사용자별로 저장")대로 저장 방식을
  골랐다. 나중에 "방금 열린 건물" 알림(해금 피드백)을 붙일 때도 저장된 `unlocked_at`이 쓸모 있다.

## 한계 (알고 둔 것)

- `theme`와 `village` 패키지가 서로를 안다: `ThemeService`가 `VillageService`를 부르고, `VillageService`는 완료 테마 수를 세려고
  `theme.repository.ThemeProgressRepository`를 읽는다. 스프링 빈 순환은 아니라서(`VillageService`가 `ThemeService`를 쓰지
  않는다) 동작에는 문제가 없다. 해금 조건에 테마 완료 외의 것이 생기면 이 방향 의존을 다시 본다.
- 집 내부 화면이 아직 없어서, 열린 집을 누르면 지금은 `/chat/home`(대화창 뼈대)으로 이동한다. 집 내부 화면은 따로 만든다.
- 테마 완료 API만으로는 하루 1테마 제한 때문에 상점(3개)까지의 흐름을 한 번에 통합 테스트할 수 없다. 서비스 규칙과 호출 연결을
  따로 검증했다.
- 마을 진입 직후 건물 목록 응답이 오기 전까지 잠깐 모든 간판이 잠금으로 보일 수 있다.
- `user_building`의 `user_id` 외래키는 `theme_progress`처럼 `ON DELETE CASCADE`가 없다. 회원 탈퇴는 `users` 행을 지우지
  않는 소프트 삭제(`0006`)라 지금은 문제가 없다. 나중에 사용자 행을 실제로 지우게 되면 두 표를 함께 처리해야 한다.
