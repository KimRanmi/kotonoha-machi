# 0015. 캐릭터 색 팔레트: 서버 한 곳에서 관리하고 프런트는 응답으로 칠한다

- 날짜: 2026-11-05
- 상태: 확정(구현함, Docker로 띄운 실제 화면 확인은 아직)

## 배경

캐릭터 색(피부색·머리색·옷 색·신발 색)을 프런트에 색 이름·한글 이름·색상값 상수로 따로 두었더니, 색을 바꿀
때마다 백엔드 enum과 프런트 상수를 같이 고쳐야 했다. 옷 색을 11색→파스텔 8색으로, 신발을 파스텔로 정리하는
동안 이 이중 관리가 불편했다.

## 검토한 선택지

- **A. 지금 그대로(양쪽에 상수)**: 단순하지만 항상 양쪽을 맞춰야 한다.
- **B. 서버가 이름·한글 이름·색상값을 내려주고 프런트는 받은 대로 그림(채택)**: 선택지 API가 이미 있어 응답
  모양만 바꾸면 된다. 팔레트가 한곳에 모인다.
- **C. DB에 색상값(`#RRGGBB`)을 직접 저장**: 색을 삭제해도 마이그레이션이 필요 없다. 반면 서버가 허용 색을
  제한하려면 저장 시 허용 목록 검사를 따로 넣어야 한다. 이번에는 저장 값(enum 이름)과 DB를 바꾸는 비용이
  커서 채택하지 않았다(필요해지면 재검토).

## 결정

- 피부색·머리색·옷 색·신발 색 enum이 한글 이름(`label`)과 색상값(`hex`)을 가진다(`AvatarColor` 인터페이스).
  `GET /api/users/me/avatar/options`의 색 목록은 `{value, label, hex}` 배열이다.
- DB에는 여전히 enum 이름만 저장한다. 색을 **삭제·이름 변경**할 때는 Flyway 마이그레이션으로 옛 값을 옮긴다
  (V13·V15 참고).
- 프런트의 색 축 타입은 `string`으로 둔다(서버가 준 이름을 그대로 쓰므로 목록 사본이 필요 없다). 옷 종류와
  헤어스타일은 이름마다 프런트에 그리는 코드가 있어 이름 목록 타입을 그대로 둔다. 한글 이름표가
  `Record<옷 종류, 문자열>`이라 새 이름을 추가하고 이름표를 빼먹으면 컴파일에서 잡힌다.
- 서버가 준 팔레트에 없는 색 이름이 오면(배포 불일치 등) 회색으로 칠해 화면이 깨지지 않게 한다.

## 나중에 재검토할 조건

- 색 삭제 때문에 마이그레이션이 계속 생기면 C안(색상값 저장)을 다시 검토한다.
