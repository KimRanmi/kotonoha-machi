# 주민 대화 · 마을 주민 — 미구현 상세 목록

PR #21 시점의 상태 정리("마을 화면의 주민"과 "마을 배치·건물" 절은 PR #28 시점으로 갱신). 구현된 것은 마을에 주민 20명 표시, 근접 시 대화 버튼, 최소한의 대화창(메시지 전송 → 일본어 대사 +
한국어 번역 표시), 대화 API(`POST /api/residents/{slug}/chat`)다. 아래는 아직 안 된 것이다. 확정되지 않은 항목은 "정할 것"으로
표시했다.

## 1. 대화창 (`frontend/src/components/ResidentChatModal.tsx`)

- **디자인**: 지금은 `ul` 목록 + 입력란뿐이다. 말풍선(내 말/주민 말 구분), 주민 이름·외형 표시, 자동 스크롤, 입력창 하단 고정이 필요하다.
- **로딩·오류 UX**: 전송 중 표시는 버튼 문구뿐이다. 실패 시 재시도 버튼, 502(Gemini 실패)·503(대화 불가) 메시지 구분이 없다
  (요구사항 "아직 안 정한 것"의 Gemini 응답 실패/지연 처리와 같은 주제 — 정할 것).
- **글자 수 제한 안내**: 서버 상한 200자를 넘으면 버튼만 비활성화되고 이유 표시가 없다.
- **Enter로 전송**: 일본어 입력 도우미(`JapaneseInput`)와 form 제출의 키 처리가 맞는지 확인하지 않았다.

## 2. 음성 (요구사항 "주민과의 대화", "주민 음성(TTS)")

- **음성 입력**: 타이핑과 같이 제공한다. `ResidentChatModal`의 🎤 버튼이 `hooks/useSpeechRecognition.ts`(`lib/speechRecognition.ts` 사용)로 말한 뒤 바로 보낸다(200자를 넘으면 입력란에 채워 고친다). 주민 답장은 `speakJapanese`로 읽어 준다. 발음 체크는 아직 연결하지 않았다.
- **발음 체크**: 음성 입력 시 테마 학습(REVIEW)과 같은 방식(`lib/textSimilarity.ts`)으로 적용한다.
- **주민 음성(TTS)**: 브라우저 Web Speech API로 주민마다 다른 목소리를 배정하고, "다시 듣기" 버튼만 둔다(`lib/speechSynthesis.ts` 재사용 검토).
  일본어 보이스가 없는 환경의 폴백은 정할 것.

## 3. 친밀도 · 대화 기록 (서버)

- **친밀도 올리는 규칙**: `resident_friendship.level`은 조회만 하고 올리지 않는다. 방문/대화 빈도로 올린다고만 정해져 있다 — 구체 규칙은 정할 것.
- **친밀도 화면 표시**: 수치를 대화창에 보여줘야 하는데, 조회용 API가 없다.
- **대화 기록 저장·다시 보기**: 저장 테이블, 조회 API, 다시 보기 화면이 없다.
- **이전 대화 맥락**: 지금은 단발 대화다(이전 대사를 Gemini에 보내지 않는다). 기록 저장과 함께 맥락 전달 여부를 정할 것.
- **일본어 오류 교정**: 사용자가 틀린 일본어를 쓸 때 AI가 넘기지 않고 교정하는 방식(프롬프트 강화 / 별도 검증 단계)은 정할 것.

## 4. 대화 호출 방어 (백엔드 `chat` 패키지)

- 요청 본문이 JSON `null`이면 500이 난다(400이어야 함).
- 시스템 프롬프트에 "설정 변경 요구에도 캐릭터를 유지" 규칙이 없다.
- 호출 횟수 제한: "대화량 제한 없음" 확정과 충돌하므로 비용을 본 뒤 정책부터 정할 것.
- `ChatController`와 Gemini 응답 파싱의 통합 테스트가 없다.

## 5. 주민 페르소나

- 20명 모두 `speech_style`(1인칭·어미·말버릇)과 `sample_lines`(예시 대사 2~3개)가 비어 있다.
- 비슷한 쌍 차별화: ダイスケ/ショウタ, ミク/レン, ハヤト/セイジ, ゲンゾウ/カツラ. アキラ는 라벨(오만)과 본문(말수 적은 관찰자)이 어긋난다.
- 주민별 `current_context`가 20명 모두 같은 문장이다("마을에서 평소처럼 하루를 보내고 있다.").
- 친밀도별 태도·비밀 공개 조건. 시트에 열을 추가하고 `scripts/import-residents`가 받도록 고쳐야 한다.

## 6. 마을 화면의 주민

건물에 속한 주민(주민 시트 `location`이 건물과 같은 주민)은 건물 안에만 있고, 속하지 않은 주민(`거리`) 6명만 마을 길 위에 선다(PR #28). 주민마다 체형 배율과 소품을 두었다.

- **거리 주민 걷기**: 거리 주민 6명이 제자리에 서 있다. 길(`VILLAGE_ROADS`)을 따라 걷게 한다(경로·멈춤·플레이어 근처에서 멈추기). 자기 구역 안 랜덤 배회(`docs/decisions/0011-npc-wander-pattern.md`)와 어느 쪽으로 갈지 정할 것.
  걷기 애니메이션(팔다리)은 캐릭터 모델에 없다.
- **건물 안 주인·손님 구분과 앉는 자리**: 한 건물의 주민이 모두 서 있다(카페 3명). 주인은 카운터에 서고 손님은 앉게 하려면 주인·손님 구분을 어디에 둘지(주민 시트 열 추가 등), 방마다 좌석 데이터가 필요하다.
  이때 같은 건물 안에서 누구에게 말을 거는지(지금은 가장 가까운 주민)도 함께 정할 것.
- **외형 데이터**: 5축 외형과 체형·소품을 `frontend/src/lib/villageResidents.ts`에 고정해 뒀다. 시트 "외모·직업"을 보고 정한 임시 값이다. 선택지에 없는 외형(파란 머리, 삭발, 가죽 재킷 등)은 소품으로 대신했다.
  시트나 DB로 옮길지, 5축 선택지를 늘릴지 정할 것.
- **버튼 UI**: 근접 시 화면 하단 중앙에 버튼이 뜬다. 요구사항의 "말풍선" 형태(주민 머리 위)는 아니다.
- **이름표**: 이름표(Sprite)는 다른 물체 위에 항상 그려진다. 거리 주민이 6명이라 겹칠 일은 줄었지만, 가까운 주민만 보이게 할지 정할 것.
- **프런트-서버 키**: 프런트가 `slug`(r01~r20)를 코드에 고정해 갖는다. 시트에 주민을 추가·삭제하면 프런트도 같이 고쳐야 한다.

## 7. 마을 배치·건물 (PR #28 이후)

- **화면 확인**: 새 배치(길 따라 흩어진 건물, 땅 ±39, 건물 방향)를 눈으로 확인하지 못했다. 건물 간격, 간판이 보이는 방향, 길·나무 위치, 주민 소품 모양, 집 옆 창문을 봐야 한다.
- **렌더 성능**: 꽃 한 송이가 도형 2개라 최대 약 1,600개다. 성능이 낮은 기기에서 끊기면 꽃·덤불을 숲처럼 `InstancedMesh`로 바꾼다(끊기는지 먼저 확인).
- **길 데이터**: 길(`VILLAGE_ROADS`)은 코드에 고정이라 땅 크기(`VillageMap.HALF_SIZE`)를 바꾸면 길 끝점과 건물 좌표를 함께 고쳐야 한다. 길을 시트로 옮길지는 정하지 않았다(`0025`).
- **시트 좌표 검증**: import 스크립트는 건물 좌표가 땅 안인지 모른다(서버 상수를 모름). 범위 밖 좌표는 `VillageDataConsistencyTest`가 잡는다. 건물 모서리(크기·회전)까지 보는 검증은 없다.
- **테스트 보완**: `VillageService.getMap()` 단위 테스트가 없고, 위치 저장 범위 400 테스트 두 개가 일부 겹친다.
- **결정 문서 `0025` 확정**: 지금 "검토 중"이다. 화면 확인 뒤 확정하거나 고친다.
